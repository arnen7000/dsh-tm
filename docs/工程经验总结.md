## 1. 项目形状

### 1.1 规模（截至 2026-11-01）

| 文件 | 行数 | 职责 |
|---|---|---|
| `dsh_manager.pyw` | 5,400 | GUI + 运行期逻辑（唯一入口） |
| `dsh_uninstall_ops.py` | 1,159 | 卸载：停进程 → 备份 → 删产物 → 改配置 |
| `dsh_install_ops.py` | 1,150 | 装槽 / 纳入：npm、回滚、复核 |
| `dsh_adopt.py` | 834 | 纯算法：扫已装、槽位规划、占位符 |
| `dsh_kill.py` | 667 | 杀进程内核：枚举 → 签名核对 → 回退 |
| `dsh-tm.py` | 483 | CLI（不 import GUI） |
| `dsh_health.py` | 383 | 槽体检（只读） |
| `dsh_registry.py` | 188 | npm 版本列表 |
| `dsh_drift.py` | 185 | 插件/配置漂移 |
| `dsh_ui_prefs.py` | 135 | 界面偏好（纯函数） |
| **合计** | **约 10,600** | 不含测试 |

测试侧：**12 个回归脚本、850+ 条断言**，`check-all.ps1` 6 项静态检查 + 11 套回归，`pre-commit` 另跑一套脱敏回归。

### 1.2 三条结构性决定（决定了后面所有写法）

**① `.pyw` 不可 import，所以纯逻辑必须拆出去。**

`dsh_manager.pyw` 在**模块级**就建 Tk 窗口、读配置、起线程。任何 `import dsh_manager` 的尝试都会开一个真窗口。于是：
- 能单测的东西一律下沉到 `dsh_*.py`（`adopt` / `ui_prefs` / `registry` 是纯函数，直接跑）；
- 留在 `.pyw` 里的逻辑，用**静态断言**测（正则抽函数体，见 §4.2）；
- CLI 走第三条路：`dsh-tm.py` **不 import GUI**，只复用纯逻辑模块。

> 代价要认：`.pyw` 里有 5,400 行无法被直接调用测试。这是这个技术栈的固有约束，不是设计失误——但它意味着 §4.2 那套静态断言不是"凑数"，是唯一的护栏。

**② 槽路径一律占位符。**

`config.json` 里写 `<base>/dsh-versions/dshV1/...`，不写展开后的绝对盘符路径。写用 `portable_path()`，读用 `_expand_slot_path()`。这样换用户名、换盘符、整个目录搬走都不断链。

**③ 一个 `config.json` 是唯一事实来源。**

端口、路径、浏览器、`extra_args` 全在里面。GUI、CLI、卸载脚本、体检读的是同一份。**任何"我也记一份在内存里"的做法都会在改配置后失效**——见 §3 第 6 条。

## 2. 开工前必须回答的六个问题

这六个问题没答案就动手，后面一定会返工。每一条都是这个项目里真实返工过的。

### Q1 谁是唯一事实来源？

`config.json`。所以：
- 装完槽**先写配置再复核形状**，不靠内存里那个 dict；
- 槽键分配必须 `_next_free_slot_key_live()` **读盘**，不能用启动时的快照 `SLOT_KEYS`；
- 界面上的"显示哪几个槽"是**偏好**，不是事实——隐藏 ≠ 卸载，`SLOT_KEYS` 永远全量。

### Q2 这份状态归谁管？

三种归属必须分清，混了就出 bug：

| 归属 | 例子 | 谁负责 |
|---|---|---|
| 管理器自己的 | 界面顺序、日志、`dsh-manager.log` | 可以随便改 |
| 槽的 | `.dsh-home`、`node_modules`、三件 bat | 只在装/卸/换版本时动，且要先备份 |
| 系统的 | PATH、注册表、全局 npm 包 | **一律不碰** |

这个项目从"装到全局 npm"改成"每槽本地安装"，本质就是把状态从第三类搬到第二类。搬完之后，用户机器上其它用 node 的软件才不会被牵连。

### Q3 失败时谁来收尸？

每一次"写了一半"的操作都要回答：失败后磁盘上留下什么？

- 装槽失败 → `_drop_partial_install()` + `_unregister_slot()` 当场收回，**前提**是 `bin.js` 不存在且 `.dsh-home` 零文件；
- 备份失败 → 目录改名 `-INCOMPLETE` 并 `raise`；改名也失败就写 `_INCOMPLETE.txt`；
- 纳入失败 → 原安装一个字节都不动（先复制用户数据并核对，再复制几百 MB 程序）。

> **不要放宽"空壳"的判据**。判据一松，就等于允许删用户手工修过的目录。

### Q4 这条路径能不能写成占位符？

凡是会进 `config.json` 的路径，都要问一遍"换台机器还认得吗"。

这个项目在这条上栽过一次：`build_slot_config()` 里 `node_exe` / `bin_js` / `dsh_home` 都过了 `portable_path()`，唯独 `temp_dir` 漏了。结果是——换用户名时三个路径好好的，临时目录断链，而且界面上完全看不出来。

### Q5 这个结论能不能被自动验证？

"应该没问题"不算结论。要么有一条断言，要么有一条回归。

反面例子：曾经有一条断言写的是"bat 里不含 `DSH-manager`"（旧项目名），项目改名后这条**永远为真**——假绿。后来改成用当前仓库目录名 + 绝对路径去断言。

### Q6 用户看不到的那一层，出错了怎么让人看见？

`.pyw` 用 `pythonw.exe` 启动，**没有控制台**。所以：
- `print()` 等于什么都没发生；
- 致命错误必须 `messagebox`，不能只写日志；
- 反过来，配置自愈这种"已经在恢复"的事，也必须弹框——否则用户看到的是"配置被静默替换了"。

这条踩过：配置解析失败时，代码已经用示例模板重建了配置，但因为 `log()` 还没定义而抛 `NameError`，弹框永远出不来。修法是加一个只依赖已定义符号的 `_boot_log()`。

## 3. 七类反复咬人的坑（按代价排序）

| # | 坑 | 一句话后果 |
|---|---|---|
| 1 | `.bat` 的编码与行尾 | 中文撕裂成非法命令，`rc=255`，双击闪退 |
| 2 | 占位符"写一半" | 换机器时只有某个字段断链，且界面看不出 |
| 3 | 把 junction 当符号链接 | 备份体积翻倍、耗时 4 倍；删除会穿透到目标 |
| 4 | 子进程输出解码 | 异常被静默吞掉，报错指向完全无关的地方 |
| 5 | 幂等与半成品 | 目录里长出 `-2` 残壳，用户以为装了两个版本 |
| 6 | 内存快照当磁盘真相 | 改完配置点启动报 `[WinError 2]` |
| 7 | `ctypes` 的 last-error | 单实例保护误判，窗口一闪不出 |

### 3.1 `.bat` 必须 GBK + CRLF + 无 BOM

`cmd.exe` 按系统 ANSI 代码页（中文 Windows = GBK）**逐字节**解析 `.bat`。存成 UTF-8 时，中文的字节序列会被当成命令的一部分，相邻两行 `REM` 直接撕裂。

三个必须一起满足的条件，缺一不可：

1. **GBK 编码**（不是 UTF-8）；
2. **CRLF 行尾**（LF-only 在某些机器上会吞行）；
3. **无 BOM**。

`chcp 65001` **救不了**——它只改变后续输出的代码页，改变不了 cmd 已经按 GBK 解析脚本内容的事实；切页后 PowerShell 回显的 UTF-8 字节又被按 GBK 解释，变成第二重乱码。

落地方式：写入点只有两处（主程序的 `_write_bat` 与 `dsh_install_ops.py`），回归 `test-bat-text.py` 守着；`fix-bat-encoding.py --check` 查仓库里的 bat，`--slots` 查各槽里生成的三件 bat。

> 槽里的 bat 不在仓库里，只查仓库会漏——这正是当年"`dsh-cli.bat` 双击没反应"漏网的原因。

### 3.2 占位符要"写全"，不是"能写"

见 §2 Q4。补充一条判断方法：**枚举**。`config.json` 里每个槽的路径字段是固定的四个（`node_exe` / `bin_js` / `dsh_home` / `temp_dir`），测试就断言这四个全部以 `<base>/` 开头，外加一条"安装根之外的 `temp_dir` 原样保留"。

只测"`bin_js` 是占位符"是不够的——漏的那个字段恰恰不在你测的名单里。

### 3.3 `os.path.islink()` 认不出 junction

dsh 的插件目录是 **junction**（不是符号链接）。这件事带来三个连锁后果：

| 你以为 | 实际 |
|---|---|
| `os.path.islink(p)` 能判断 | **不能**。要读 `os.stat(p, follow_symlinks=False).st_file_attributes & 0x400`（`FILE_ATTRIBUTE_REPARSE_POINT`） |
| `shutil.copytree` 复制的是链接 | 会**跟进去**：实测 487 MB → 942 MB、14 分钟，而且复制出来的是副本不是链接 |
| `shutil.rmtree` 只删链接本身 | 会**递归删目标内容**，可能删到槽外 |
| `os.walk(followlinks=False)` 能挡住 | 挡不住 |

正确做法：
- 备份走 `robocopy /E /XJ`（`/XJ` = 不跟随 junction），失败退回逐文件实现；
- 删除走自己实现的 `_force_rmtree()`；
- 纳入时 `collect_links` → `copy_tree_nolinks` → `relink_home`（指向旧槽的改指新槽，槽外目标原样指回，目标丢失记 `lost`）。

两个附加坑：
- `mklink` 的目标必须先 `normpath` 成反斜杠，正斜杠建不出来；
- junction 的 `readlink` 目标带 `\\?\` 前缀，不剥掉就匹配不上。

### 3.4 `text=True` 会静默吞掉解码失败

`subprocess` 用 `text=True`（或 `universal_newlines=True`）而不指定 `encoding`，会按 locale **严格**解码。中文 Windows 的 `netstat` / `taskkill` 输出是 CP936，而进程内被 `PYTHONUTF8=1` 固定成 UTF-8 → 解码失败。

最坑的地方：`subprocess` 把异常吞在内部线程里，**只把 `stdout` 置成 `None`**。于是症状与真因完全无关：

```
'NoneType' object has no attribute 'splitlines'
```

正确做法是取字节回来自己解（`utf-8` → `cp936` → `replace`），见 `dsh_kill.run_capture`。`check-all.ps1` 有一条静态检查专门拦这个写法。

### 3.5 幂等与半成品

`dshV1-2` 这种名字有**两个**来源，别混：

1. **卸载收尾 `rmdir` 失败**留下的零文件空壳 → 下次装槽会 `_reuse_empty_shell()` 复用；
2. **装到一半失败**（目录里有 `npm init -y` 生成的 `package.json`，不算空壳）→ 失败路径当场收回。

第 2 条的收回有前提：`bin.js` 不存在 **且** `.dsh-home` 零文件。这两个条件同时满足才敢删——否则可能删掉用户手工修过的目录。

启动时 `_log_orphan_shells()` 只报不删。**管理器不替用户做删除决定。**

### 3.6 内存快照 ≠ 磁盘真相

`SLOT_KEYS` 是**启动时的快照**。改完 `config.json` 之后，内存里的路径全是旧的，点"启动"就会报 `[WinError 2]`（找不到可执行文件）——而文件其实好端端在那儿。

规则：
- 槽键分配、端口分配一律**读盘**；
- 改配置之后必须 `_reload_config_after_change()` 重启管理器（代码改动也不热生效）；
- 改槽目录 / `config.json` 之前，先确认管理器**没在跑**。

### 3.7 `ctypes` 判 `GetLastError` 必须显式捕获

```python
# 错：windll 句柄不捕获 last-error，GetLastError() 读到的是线程残留值
ctypes.windll.kernel32.CreateMutexW(...)
ctypes.windll.kernel32.GetLastError()

# 对：
k32 = ctypes.WinDLL("kernel32", use_last_error=True)
k32.CreateMutexW(...)
ctypes.get_last_error()
```

这个错的表现是单实例保护误判——管理器窗口一闪就没了，看起来像崩溃。

## 4. 测试：把"看不见的约定"变成可执行的断言

### 4.1 四层，各管一段

| 层 | 例子 | 管什么 |
|---|---|---|
| **纯逻辑单测** | `test-adopt-logic` / `test-ui-prefs` / `test-cli` | 算法正确性，毫秒级，无副作用 |
| **静态断言** | `test-manager-logic`（282 条） | `.pyw` 里那些**没法 import 的函数**：正则抽函数体，断言关键结构 |
| **真进程** | `test-standalone` | 真的 `cmd.exe` + 真的 `node.exe` 跑生成的 bat |
| **环境快照** | `test-health` / 卫生闸 | 体检前后磁盘快照必须一致；回归不许在真实盘留东西 |

### 4.2 静态断言怎么写才不是自欺

`.pyw` 不可 import，所以只能读源码文本。三条纪律：

1. **断言"存在"也要断言"不存在"**。比如"降级提示不得再劝用户提权"，就断言 `"以管理员身份运行" not in src`——只断言新文案出现，旧文案删没删是不知道的。
2. **注释不算代码**。写个 `_code_only()` 把注释行剥掉再断言，否则"历史上曾经这样"的注释会让断言误判。
3. **别断言恒真的东西**。见 §2 Q5 的假绿例子。

### 4.3 真进程测试的价值

`test-standalone.py` 做的事：把生成 bat 时的 `BASE_DIR` 指向一个**不存在的目录**，等价于"管理器已经被删掉"，然后真跑 `cmd.exe` 去执行那些 bat。

它守的是一条产品承诺——**管理器删了，各版本仍能自己跑**。这条承诺没法用单测证明，只能真跑。

### 4.4 卫生闸：测试不许污染真实盘

回归里有两个函数会 `makedirs`（装槽、纳入）。历史上每跑一次总检（含每次 `git commit` 的 pre-commit 钩子），临时目录根下就长出 `dshV1` / `dshV2-2` / `dshV9` 一串空文件夹——`dshV9` 从来不是真的槽，它只存在于测试脚本里。

现在的做法：`check-all.ps1` 跑回归**前后各拍一次目录快照**，有变化就红。

配套的做法是测试自己设 `DSH_TEMP_NO_REAL_DISK=1`，让候选盘列表为空，临时目录落到测试自己的 tmp 里。

### 4.5 五道门禁

```
改完代码 → py-syntax-check（内存编译，连 SyntaxWarning 也算失败）
        → check-all -Fast（编码 / 敏感文件 / token / 链接 / 语法）
        → check-all（+ 11 套回归 + 卫生闸）
        → pre-commit（另加 test-log-mask 脱敏回归 + 用户名扫描）
        → git push
```

关于"语法警告也算失败"：docstring 里写 `\d` 会触发 `SyntaxWarning: invalid escape sequence`。这种警告不影响运行，但会在别人机器上变成噪声，所以升级成失败。

## 5. 发布前体检：从"新用户第一次运行"倒推

### 5.1 测试全绿 ≠ 能发布

这是这次最值钱的一条。总检 6/6、回归全 PASS、脱敏零命中——**但新用户第一次运行仍然会坏**。

原因很简单：**绿的是"已经写进测试的路径"，而"第一次运行"这条路径从来没被测试覆盖过**。

### 5.2 这次真实抓到的三类问题

| 类型 | 实例 | 为什么测试没抓到 |
|---|---|---|
| **必然崩** | 旧安装脚本在零槽配置上赋值 `$null.label`，而脚本开头 `$ErrorActionPreference="Stop"` → 直接终止 | 那个脚本已经标记 LEGACY，没人跑过它 |
| **静默写错** | `temp_dir` 漏了 `portable_path()` | 断言只覆盖了另外三个字段 |
| **文档与代码对不上** | 架构文档写"三条隔离轴"，README 写"五条" | 链接检查只验文件在不在，不验内容对不对 |

### 5.3 体检清单（可复用）

**第一步：跑总检。** 全绿才有资格往下走。

**第二步：脱敏。** 不是"看一眼"，是**扫**：

```bash
# 扫「真实用户名」与「写死的本机盘符路径」
git ls-files -z | xargs -0 grep -nIE '<用户名>|[A-Za-z]:[\\/]Users[\\/][^<]'
```

注意排除合法的 `C:\Program Files`（浏览器/node 探测路径）和 `C:\Users\<占位符>`。

**第三步：假装自己是新用户，从零走一遍。**
- 新 clone 到空目录 → 双击入口 bat → 会看到什么？
- 装第一个版本 → 会弹什么？失败会长什么样？
- 这一步不需要真的跑完，**读一遍入口脚本就能发现大部分问题**（这次就是这么发现崩溃的）。

**第四步：文档与代码对账。**
- 数一遍：代码里 `MAX_SLOTS = 6`，文档里有没有写"最多 5 槽"？
- 数一遍：回归有几套？文档里写的是几套？
- 端口序列对不对得上（4080 / 5080 / 7080 / 9080 / 6081，且文档里写的「避开 6080/8080」和代码一致）？

**第五步：删遗留。**
判断标准很简单：**这个文件描述的还是当前这个产品吗？** 如果它描述的是上一代模型，留着只会让人困惑——哪怕它已经标了 `[LEGACY]`。

这次删了 8 个文件（旧安装器、旧离线打包、旧卸载仿真、旧离线配置），仓库从 60 个受控文件降到 54 个。

### 5.4 一条经验

> **"标记为已停用"不是处理，是欠账。**
> 停用的脚本仍然会被新用户双击；停用的文档仍然会被搜索引擎索引。要么修好，要么删掉，git 历史里永远找得回来。

## 6. 文档体系：一个事实只写一遍

### 6.1 分工

| 文档 | 只回答 |
|---|---|
| `README.md` | **是什么、怎么用**（全场景，含故障速查） |
| `docs/架构与维护说明.md` | **为什么是这样**（给改代码的人） |
| `docs/dsh管理器使用说明.md` | 按钮语义、配置字段 |
| `docs/常见问题.md` | **出问题了怎么办** |
| `docs/isolated-install-runbook.md` | 手工做一遍隔离安装 |

### 6.2 反模式：同一句话抄五份

这个项目栽过：隔离轴的数量在 README 写"五条"、在架构文档写"三条"，因为两边各写各的。

**规则**：同一个事实，选一个"权威位置"，其它地方**只链接不复述**。

### 6.3 三种可自动化的校验

1. **链接能落地**：`check-all` 逐个 `Test-Path`，44+ 个相对链接全部验过；
2. **锚点能跳转**：README 内部 `](#...)` 与标题 slug 对账（这次查出 17 个锚点，全部命中）；
3. **计数与代码对账**：回归套数、槽上限、端口序列——这三类数字最容易过期。

### 6.4 文档里不许出现的

- 本机绝对路径（用 `<base>` / `<home>` / `<self>` 占位符）；
- 真实用户名；
- 明文 token（日志里也要打码）；
- 只对某台机器成立的"现状"（这类内容单独放，不进仓库）。

`pre-commit` 会拦用户名；`check-all` 会拦 token 与断链。

## 7. 和 dsh 插件开发的对照

做 `dsh-workbuddy-model` / `dsh-workbuddy-websearch` 时积累的经验，有一部分能直接搬过来，有一部分搬不动。分清这两类是省时间的关键。

### 7.1 可以直接搬的

| 插件侧的做法 | 在这个项目里怎么用 |
|---|---|
| **零本机信息是头号红线** | 一样。而且这里的"本机信息"还包括槽路径——所以才有占位符铁律 |
| **发版前 60 秒清单** | 演化成 §5.3 的五步体检 |
| **每条硬约束都要有"守护者"** | 一张"规矩 → 谁守着它"的对照表，比写在文档里靠自觉有效得多 |
| **错误要能分类**（带 `code`） | 卸载/安装的失败都返回 `(ok, msg)` 并区分"拒绝执行"与"执行失败"，上层才好决定重试还是放弃 |
| **包内容变了就 bump 版本** | 这里对应"改了代码必须重启管理器"——不热生效，别指望改了立刻看到 |
| **测试分层**（单测 / 集成 / 真机） | 一样，只是把"真机"换成"真 cmd + 真 node" |
| **结论先行**（先给判断，再给过程） | 日志与体检报告都按这个写：`[错误]/[提示]` 打头 |

### 7.2 搬不动的

| 插件侧 | 为什么这里不适用 |
|---|---|
| patch 里 `config` 要复述同层其他键 | 那是 Cordis 的**整体替换**语义，属于宿主框架，本项目不碰 |
| provider id 唯一 / 设置命名空间 | 同上，插件注册面特有 |
| 不声明 peer 版本区间 | 这里没有 peer 依赖；对应的问题是"node 版本红线 22.19" |
| pnpm 24h 新版本冷却 | 只有 `dsh plugin add` 走 pnpm，管理器直接 `npm install` |

### 7.3 最本质的差异

| | 插件 | 这个项目 |
|---|---|---|
| 运行位置 | **加载进宿主进程** | **起独立子进程** |
| 崩溃影响 | 拖垮整个 dsh | 只死一个版本 |
| 状态同步 | 内存对象，实时 | 磁盘 `config.json`，需要读盘/重载 |
| "它还在跑吗" | 不用问 | 必须回答：靠**进程签名 + 端口**，不靠 pid 文件 |
| 卸载干净 | 从 profile 里摘掉 | 停进程 → 备份数据 → 删产物 → 改配置，四步都要能重入 |

最后一行值得展开：**判断"这个 node 进程是不是我的"不能靠宽松匹配**。这个项目的闸门是 `dsh_kill.find_version_pids(sig, port)`——槽 `bin.js` 的绝对路径 + 端口，两个条件同时满足才算。端口被非 dsh 进程占用时**绝不 kill**，只告警。

## 8. 下次做同类工具的起手式

按顺序，别跳：

1. **先写 `config.json` 的形状**，再写代码。所有路径用占位符。
2. **先定"失败怎么收尸"**，再写"成功路径"。每个写盘操作配一个回滚。
3. **先把纯逻辑拆成独立模块**，保证能单测。GUI 文件只做"读配置 → 调模块 → 画界面"。
4. **先写体检（只读）**，再写安装。体检让你知道"什么样算装好了"，安装才有验收标准。
5. **先写卫生闸**，再写回归。否则测试自己会污染真实盘，而且很难查。
6. **先定门禁，再写代码**：编码规则、敏感文件、链接、断言——让机器记住，别靠人记。
7. **发布前从"新用户第一次运行"倒推一遍**，这一步不能省（见 §5）。
8. **同一事实只写一遍**，其它地方链接过去。

## 9. 和 AI 助手协作的几条（附）

这个项目大部分代码是和人机协作写出来的，有几条经验值得留：

- **给它"判据"，别给"意图"**。"界面要好看"没法验证；"卡片标题居中、状态行收到 26px、拖动时不能重建卡片"可以。
- **让它先读 `docs/架构与维护说明.md`**，比读 README 有用——README 讲怎么用，架构讲为什么。
- **改动前让它先说"我准备改哪几个文件、为什么"**。这个项目的返工大多来自"改对了功能，改错了边界"。
- **代码改动不热生效**。让它改完提醒你重启，不然你会对着旧界面怀疑人生。
- **别让它碰 `config.json`**，除非你确认管理器没在跑（§3.6）。
