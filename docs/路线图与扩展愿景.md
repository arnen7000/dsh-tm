# 路线图与扩展愿景

> **这份文档给谁**：给**接手开发的另一个 agent**（或另一个人）。
>
> **它记什么**：已经想清楚的判断、已经验证过的技术事实、以及**还没想清楚的问题**。不是承诺清单——没写进来的功能就是没打算做。
>
> **它不依赖任何对话上下文**：读完这份文档 + §6.1 列的三份文档，就能独立开工。凡是需要"当时讨论过才知道"的内容，都已经写进来了；没写的，就是还没定。
>
> **怎么用**：§1 是别重做的东西；§3 是最大的一块未开发地；§6 是下次开工的入口。

---

## 0. 一句话现状

dsh-tm 现在是一个**托管器**：管 1~6 份互相隔离、各自带 node 运行时、可随时丢弃的 dsh 环境。

往下走有两个方向，优先级不同：

| 方向 | 一句话 | 状态 |
|---|---|---|
| **A. 可被调用** | 让别的 agent（含另一个 dsh）能用命令行的方式驱动它 | **走了一半** |
| **B. 评估试验台** | 用这 5 份干净环境去做版本/插件的对比实验 | **没动，但地基已经够** |

---

## 1. 已经完成的地基（别重做）

### 1.1 CLI

`dsh-tm.py`，**不 import GUI 模块**，可在无图形环境（CI / 计划任务）里跑。

| 命令 | 作用 |
|---|---|
| `list` / `status [槽]` | 列出槽与运行状态 |
| `start <槽>` / `start --all` | 启动（`--wait <秒>` 等端口监听） |
| `stop <槽>` / `stop --all` | 停止 |
| `url <槽>` | 打印带 token 的入口 URL |
| `health [槽] --deep` | 槽体检（只读） |
| `kill-stray [--yes]` | 清理**槽外**的 dsh 残留（排障动作，缺省只打印计划） |

公共参数：`--config <路径>`、`--verbose`。退出码：`0` 成功 / `1` 有失败 / `2` 用法错误 / `3` 配置错误。

### 1.2 三块只读能力

- **槽体检** `dsh_health.py`：程序入口 / node / 数据目录 / 启动脚本 / 依赖齐不齐 / 原生模块 / node 版本 vs `engines` / 跨槽端口冲突。**不写盘。**
- **漂移检测** `dsh_drift.py`：给每个槽拍指纹（插件名+版本、`dsh.profile.bundles`、几个 yml 的哈希），约 10 秒比一次，变化写 `[变更]` 日志。
- **槽形状复核** `slot_shape_problems()`：自带 node、`bin.js`、占位符、独立 temp、三件 bat。

这三块是方向 A 和 B 的**共同前提**——没有它们，"环境是否干净"只能靠人看。

### 1.3 验证体系

11 套离线回归 + `check-all` 6 项 + `pre-commit`。见 [`工程经验总结.md`](工程经验总结.md) §4。

## 2. 方向 A：与 dsh / 其它 agent 联合

### 2.1 要解决的问题

某个 dsh 版本出问题时，能不能让**另一个正常的 dsh**（或别家 agent）来修它？

### 2.2 分层（这是关键判断）

| 层 | 谁做 | 做什么 |
|---|---|---|
| **规则层** | dsh-tm | 只做确定性的事：体检、漂移、形状复核、重建 bat、备份/纳入、起停 |
| **智能层** | 外部 agent | 读结构化报告 → 判断根因 → 决定怎么修 |
| **契约** | CLI + JSON | 两层之间唯一的耦合点 |

**不要让 dsh-tm 自己长出一个 LLM 判断层**。它的价值恰恰是"确定、可复现、不猜"。

### 2.3 还缺什么（按重要性）

1. **`--json` 输出**。现在 CLI 打的是给人看的对齐文本，agent 解析起来很痛苦。所有命令都应支持 `--json`，输出固定 schema（含 `schema_version`）。
2. **读写分界要显式**。`health` / `list` / `url` 只读；`start` / `stop` / `kill-stray --yes` 改运行时；`install` / `adopt` / `uninstall` 改磁盘。前两类可以随便调，第三类要人确认。
3. **审计**。谁在什么时候改了什么。现在只有日志，没有结构化审计流。
4. **幂等与可重入**。装/卸已经做了，但 CLI 侧还没统一保证。

### 2.4 最小可做的一步

```
dsh-tm.py doctor --json
```

一次体检全部槽，输出机器可读的结论（每个槽 `ok / warn / error` + 具体条目 + 建议动作）。这一条做出来，外部 agent 就能接入了——不需要等其它功能。

## 3. 方向 B：评估试验台（最大的一块）

### 3.1 核心判断

> **dsh-tm 的独有资产不是 GUI，是「5 份干净、同构、可随时丢弃的环境」。**

所以它天然适合做一件事：

```
外部标准（任务集 + 判据）  ×  dsh-tm（环境 + 执行 + 计量）  →  可复现的结论
```

dsh-tm **只做运行时**（环境准备、执行、采集指标），**不自造标准**。标准由外部提供。

### 3.2 外部标准的三要素

| 要素 | 是什么 | 没有会怎样 |
|---|---|---|
| **任务集** | 题面 + 初始工作区快照 | 每次跑的起点不同，结果不可比 |
| **判据** | `check.py` 之类可客观执行的验收 | 只能靠人看，无法规模化 |
| **规程** | 跑几次、允许什么、怎么计分 | 结论是轶事，不是数据 |

### 3.3 三层难度（决定先做什么）

| 层 | 能不能做 | 关键约束 |
|---|---|---|
| **性能** | **现在就能出数**，几乎免费 | token 四分类、模型/工具时间归因、工具错误率、单工具耗时排行 |
| **质量** | 只做两档 | **强客观**（跑 `check.py`，过/不过）+ **弱客观**（结构断言，如"文件存在且能解析"）。**不做 LLM 评委** |
| **统计** | 必须做，不能省 | N ≥ 5 次重复、配对比较、随机化顺序；报**中位数与 p90**，**禁用均值**（长尾会把均值毁掉） |

### 3.4 两个实验方向

| 方向 | 固定 | 变量 | 用途 | 判据风格 |
|---|---|---|---|---|
| **A（先做）** | 同一套插件 + 同一模型 | **dsh 版本** | 回归：这个版本能不能发 | 严；任务偏旧；结论二值；重复少 |
| **B（后做）** | 同一版本 + 同一模型 | **插件方案** | 选型：哪个插件更好 | 基线必须是"禁用"；防互补/拮抗；方差大 |

**建议先做 A**：判据更严、结论是二值的、重复次数少，最容易先跑通。

### 3.5 三个必须写进结论的隐藏变量

1. **换 dsh 版本 ≠ 只换几行代码**。实际变的是整棵 `node_modules` + 内置 system prompt + 默认工具集 + profile 默认值。所以结论只能表述为「**整个发行包**层面」，不能定位到某个改动。
2. **数据污染**。用公开题（比如历年竞赛题）时，结论可能只是"谁背得好"。要么用新题，要么自出题。
3. **不可判定的任务要排除**。证明题没法自动判对错，应偏**求值 / 构造 / 可执行验证**类。

### 3.6 基准槽：绕开 `MAX_SLOTS = 6`

矩阵实验要同时存在多份环境，6 个槽会被卡死。

**基准槽**的设计：

- 不属于 `versions`，不占 `MAX_SLOTS`；
- 从快照恢复，**用完即删**；
- 与正式槽共用同一套隔离语义（自带 node、独立 `DSH_HOME`、独立 TEMP、独立端口）；
- 存放位置与正式槽分开，避免被"体检""卸载"误伤。

需要新增的东西：一个 `bench` 配置段（或独立的 `bench.json`）+ `dsh-tm.py bench run` 子命令。

### 3.7 最小可跑版本

```
bench/
  tasks/<任务>/
    prompt.md          # 题面
    setup/             # 初始工作区快照
    check.py           # 判据：退出码 0 = 通过
  runs/<时间戳>/
    score.json         # 指标 + 判据结果
    session/           # 会话文件副本
```

runner 流程：

```
恢复快照 → 起 dsh（基准槽）→ 提交 prompt → 等 turn/end
        → 收集会话文件 → 抽指标 → 跑 check.py → 写 score.json
```

产出：**退化表**

| 版本 | 通过数 | 具体哪道题退化 | 中位耗时 | 平均 token | 工具错误率 |
|---|---|---|---|---|---|

第一版建议：3–5 道自出题、每轮 3 次重复、**只做性能层不做质量层**。

### 3.8 会话指标从哪来（已实测，别重新踩）

**文件位置**：`<DSH_HOME>/sessions/<workspace>/session-<uuid>/session.v4.jsonl.zstd`

**两个必须知道的坑**：

1. 这个文件是 **N 个 zstd frame 串联**（实测一条会话 639 帧，每帧约 1.4 KB 逐条追加）。
2. `zstdDecompressSync` 和 `createZstdDecompress` **都只解第一帧**。

正确做法：按 magic `28 B5 2F FD` 逐帧切分，尝试解压成功即采用该边界。

```js
const MAGIC = Buffer.from([0x28, 0xB5, 0x2F, 0xFD]);
const parts = []; let cur = 0;
while (cur < buf.length) {
  let probe = cur + 4, done = false;
  while ((probe = buf.indexOf(MAGIC, probe)) !== -1) {
    try { parts.push(zlib.zstdDecompressSync(buf.subarray(cur, probe))); cur = probe; done = true; break; }
    catch (e) { probe += 4; }
  }
  if (!done) { try { parts.push(zlib.zstdDecompressSync(buf.subarray(cur))); } catch (e) {} break; }
}
```

**自举技巧**：Python 3.10 标准库没有 zstd，但**每个槽自带的 node ≥ 22 有 `zlib.zstd*`**。所以用槽里的 node 去解它自己的会话——零第三方依赖，不用装任何包。

**事件字段**：

| 事件 | 关键字段 |
|---|---|
| `turn/start`、`turn/end` | `data.reason.kind` |
| `step/start` | — |
| `assistant/message` | `data.usage.{inputTokens, outputTokens, totalTokens}` |
| `tool/call` | `data.callId`、`data.name` |
| `tool/result` | `data.message.toolCallId`、`data.message.isError` |
| `workspace/changes` | — |

每条事件都有顶层 `time` 与 `seq`。

> **踩过的坑**：一开始用 `d.message.id` 去 join `tool/call` 与 `tool/result`，恒为 0 —— 实际 `tool/call` 的 id 在 `data.callId`，`tool/result` 在 `data.message.toolCallId`。修正后工具耗时从 0 变成 1253 秒（占总墙钟 49.8%）。

### 3.9 一次真实会话的基线（量级参照）

单条会话、20 轮：

| 指标 | 值 |
|---|---|
| 轮次 / 步数 / 工具调用 | 20 / 181 / 243 |
| 工具报错 | 24（9.9%） |
| token 输入 / 输出 / 合计 | 2,579,835 / 93,759 / 2,673,594 |
| 输入 : 输出 | **27.5 : 1**（输入占 96.5%） |
| 每轮耗时 min / p50 / p90 / max | 18.9s / 69.4s / 398s / 624s |
| 总墙钟 | 41.9 分钟 |
| 时间归因（模型 / 工具 / 框架） | 49.9% / 49.8% / 0.3% |

**结论：输入 token 是成本的主项，不是输出。** 任何"省 token"的优化都要先看输入侧（上下文长度、工具返回体积），而不是模型输出的字数。

### 3.10 还没想清楚的问题

1. **判据怎么防刷分**？agent 可能绕过任务本身去迎合 `check.py`（比如直接写死期望输出）。可能需要"判据不在工作区里"或"多个判据交叉"。
2. **同题多次运行，工具调用路径不同，怎么比**？性能指标（token、耗时）可比，但"做了什么"不可比。是否需要归一化（比如按步数平均）？
3. **成本怎么算**？token 单价随模型变、随缓存命中变。是否只报 token 不报钱？
4. **结果放哪**？进仓库（可复现、但会变大）还是只留本地？
5. **插件方向（B）的基线怎么定**？"禁用该插件"是唯一干净的基线，但有些插件禁用后 dsh 起不来。

## 4. 明确不做的

写下来是为了省掉下次的重新讨论：

| 不做 | 理由 |
|---|---|
| 自动硬链接去重 | 收益不确定，风险（删错目标）确定 |
| 插件市场面板 | dsh 自己有；重复造且必然滞后 |
| 遥测 / 众筹数据 | 隐私红线，且样本偏差大 |
| 会话内容索引 | 用户数据，不该被工具读 |
| `--force` 跳过安全检查 | 安全闸一旦可跳过，就等于没有 |

## 5. 曾提出、优先级较低

想起来了就做，不着急：

- 定时巡检（每天体检一次，变化写日志）
- 漂移历史时间线（现在只有"变了"，没有"什么时候变的、变了什么"）
- manifest 复现装法（记录每个槽的精确依赖树，用于精确重建）
- 快照回滚（装坏了回到上一个已知good状态）
- 槽克隆（复制一个槽做实验，不动原件）
- 插件兼容矩阵（哪些插件组合能共存）
- 跨槽配置 diff（同一插件在不同槽里的配置差异）
- 取证包（一键打包日志+配置+体检结果，用于求助）
- 同版本双胞胎（同版本两个槽，验证"差异是否来自环境"）
- 混沌注入（随机杀进程/改配置，验证恢复能力）
- 会话搬运检验（把会话从 A 槽搬到 B 槽，看是否还认得）

其中**槽克隆**和**同版本双胞胎**其实是方向 B 的前置能力，做评估时大概率会先需要它们。

## 6. 下次开工的入口

### 6.0 接手时先做这四件事（约 3 分钟）

```bat
git log --oneline -20                 :: 最近改了什么，结论都在提交信息里
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check-all.ps1 -Fast
python dsh-tm.py list                 :: 当前机器上有哪些槽、什么状态
python scripts\check-env.py           :: 环境是否齐备
```

**状态的权威顺序**（冲突时按这个来，别反过来）：

```
代码 > config.json > git log > 文档
```

文档一定会滞后。发现文档与代码不一致时，**改文档，不要改代码去迎合文档**——除非代码确实错了。

### 6.1 先读什么

| 顺序 | 文档 | 为什么 |
|---|---|---|
| 1 | [`工程经验总结.md`](工程经验总结.md) | 知道哪些坑已经踩过，别再踩一遍 |
| 2 | [`架构与维护说明.md`](架构与维护说明.md) | 知道代码在哪、为什么这么分 |
| 3 | 本文 §3 | 知道要做什么、做到哪算够 |

### 6.2 从哪开始

如果做**方向 A**：先做 `doctor --json`。它一个人就能让外部 agent 接入，且不改任何现有行为。

如果做**方向 B**：先做「基准槽 + 单题跑通」。不要一上来做矩阵——先用一道题、一个版本、跑 3 次，把"恢复快照 → 跑 → 收会话 → 出数"这条链路打通。链路不通，矩阵没有意义。

### 6.3 怎么验证

任何新功能都要过现有的五道门禁（`check-all` → 回归 → `pre-commit`）。新增的采集/统计逻辑必须能在**假会话文件**上跑，不能依赖真实调用（烧 token 且不可复现）。

### 6.4 动手前的硬约束（违反会直接坏东西）

| 约束 | 为什么 |
|---|---|
| **别在管理器运行时改 `config.json`** | 内存里是旧路径，点启动必报 `[WinError 2]` |
| **代码改动不热生效** | 改完必须重启管理器，否则你会对着旧界面怀疑人生 |
| **槽路径一律占位符** | 写用 `portable_path()`，读用 `_expand_slot_path()`；但给 `cmd.exe` 读的 `.bat` **必须先展开** |
| **`.bat` 必须 GBK + CRLF + 无 BOM** | 写入点只有两处（`_write_bat` / `dsh_install_ops.py`），改一处漏一处 |
| **杀进程只走 `dsh_kill.find_version_pids(sig, port)`** | 别在别处写宽松判定当杀人依据；端口被非 dsh 进程占用时**绝不 kill** |
| **`os.path.islink()` 认不出 junction** | 要读 `st_file_attributes & 0x400`；`rmtree` 会穿透删目标 |
| **别放宽"空壳目录"的判据** | 一松就等于允许删用户手工修过的目录 |

更完整的原理见 [`工程经验总结.md`](工程经验总结.md) §3。
