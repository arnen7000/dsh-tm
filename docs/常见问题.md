## 零、安装与界面操作

### Q0a. 双击版本目录里的 `dsh-cli.bat` 没反应 / 窗口一闪就没？
- **根因（已实测定位）**：管理器生成的 bat 原本写成 **UTF-8 无 BOM**，而 `cmd.exe` 读 `.bat` 用的是
  **ANSI 代码页（中文 Windows = 936/GBK）**。两个后果叠加：
  1. 中文注释被按 GBK 解析成乱码（表面问题）；
  2. 相邻两个中文 `REM` 行时，按 GBK 的字节边界会把上一行行尾的 CRLF **吞掉/撕裂** ——
     实测 `REM 用法：... dsh-cli.bat <子命令> <参数>` 被从「双击进入」处撕成两半，
     后半截 `<子命令> <参数>` 被当成**命令**执行，`<` 触发输入重定向
     → cmd 报「命令语法不正确」rc=255 → 双击只看到窗口一闪就没。
     （UTF-8 **带 BOM** 更糟，同样 rc=255。）
- **修法**：bat 一律写 **GBK + CRLF + 无 BOM**（`dsh_manager.pyw:_write_bat` 与 `dsh_install_ops.py`
  两处写入点都已改），并把注释里的 `<子命令> <参数>` 改成方括号写法（cmd 元字符不进注释）。
  已有的槽目录里的 bat 需要用新代码重新生成一次（点「生成启动/kill/CLI bat」）。
- **验证**：新增离线回归 `scripts/test-bat-text.py`（已注册进 `check-all.ps1`）——
  断言三个 bat 可无损 GBK 编码、CRLF、注释行无 `< > | & ^`，并把 bat 真正交给 `cmd.exe` 跑一遍（只验解析），
  4 个槽实跑 `dsh-cli.bat --version` 全部 rc=0。
- **另外**：即使编码修好，**双击（无参数）也不会进入交互式 CLI** —— 实测这几个版本的 dsh
  无参数会直接 `error: --profile <name> is required` 退出。正确用法：
  `dsh-cli.bat --profile headless`（`headless` 可换成该槽 `.dsh-home\profiles\` 下已有的名字（常见是 `headless` / `web`）。
- **现状**：✅ 已落地。
- **位置**：`dsh_manager.pyw`（`_write_bat` / `_bat_text_cli`）、`dsh_install_ops.py`、`scripts/test-bat-text.py`。

### Q0b. `dsh-cli.bat` 和 `dsh.bat` 有什么区别和联系？
- **同一个程序，两种模式**：两者调的都是**同一个 npm 包** `@deepseek-ai/dsh` 的 `lib/bin.js`
  （`package.json` 里 `"bin": {"dsh": "lib/bin.js"}`），没有独立的 CLI 包。
  区别只在**传不给它的第一个子命令**：
  - `dsh.bat` → `bin.js web --host 127.0.0.1 --port <该槽端口> --no-open` —— 起 **web 服务**，浏览器访问；
  - `dsh-cli.bat` → `bin.js %*` —— **原样透传**你给的参数，走 dsh 的**命令行模式**（需 `--profile <name>`）。
- **联系 / 共同点**：环境隔离完全同源 —— 都设本槽的 `DSH_HOME`、`TEMP/TMP`、把本槽自带 `node`
  前置到 `PATH`；都由管理器用**同一批函数**（`_bat_text_start` / `_bat_text_cli`）生成，
  点一次「生成启动/kill/CLI bat」三个文件同步重生，永不脱节；端口占用互斥（同一个端口只能跑一个）。
- ** Kill 脚本**是第三件：`kill-<端口>.bat` → `dsh_kill.py --port <该槽端口>`，按**签名 + 端口**精准停止本槽，不碰别的版本。

## 零之二、卸载 / 纳入 / 移出 / 界面偏好

### Q0c. 怎么在管理器里卸掉某一个（或几个）dsh 版本？
- **答复**：点「设置 → 版本管理 → **卸载 / 移出管理**」→ 选中要卸的槽（**一次一个**，单选）→ 二次确认。
  同一个窗口里还有「移出管理（不删文件）」，见 Q0c-3。
  每个槽依次：停进程（走 `dsh_kill` 门控，只杀本槽 dsh）→ **备份** → **整个槽目录删干净**
  → 从 `config.json` 摘掉该槽。
- **备份里有什么**（2026-10-30 起）：落在 `<install_base>\dsh备份\<槽>-userdata-<时间戳>\`
  - `.dsh-home` 的**全部内容**（会话 / 设置 / 凭据 / 插件配置 profiles）
  - `_slot-package.json` / `_slot-package-lock.json`：槽根的 npm 清单 —— **装过哪些插件、
    钉的是哪个版本**全在这两份里（它们本来是要被删的程序文件）
  - `_meta.json`：槽名 / **实装版本号** / 端口 / 数据与临时目录 / 卸载时间 / `config.json` 原片段
  - `_links.json`：**跳过的 junction / 符号链接**（相对路径 → 目标）。备份不跟随链接，
    所以这份清单是"备份里少掉的那些链接"的对照表
- **备份多快**：`robocopy /E /XJ /MT:8` 多线程（不跟随 junction）。几百 MB、上万文件通常在几秒到十几秒；
  机器正在被杀软全盘扫描时可能慢一个量级，属外部因素。
- **为什么要整个删掉**：只删程序会留下 `.dsh-home` + `.tmp` 的空壳目录，下次往同一个槽装版本时
  `unique_dir` 认为名字被占，于是装出 `dshV4-2` —— 看着像"上次没卸干净"（2026-10-29 实测踩到）。
  现在备份成功后才动手，删完槽目录本身也没了，再装就是干净的 `dshV4`。
- **不会删什么**：管理器目录、别的槽、盘符根一律不碰；槽外的临时目录（`<槽根>/dsh-temp/<槽>`，
  2026-10-31 之前是 `<临时目录根>\<槽>`）不归槽所有，不动它（提示里会说明可自行清理）。
  `bin_js` 在 npm 全局 `node_modules` 下的槽 **不能按槽卸**（那里是所有全局包共用目录）。
- **备份失败怎么办**：该槽**不删任何文件、也不从配置移除**，宁可这次没卸成。
- **备份会核对**（2026-10-31 起）：拷完当场逐文件核对（相对路径 + 字节数）。
  **缺一个文件就中止** —— 该槽不删任何东西，半份备份被改名 `-INCOMPLETE` 留在原处，
  提示里写清「应备份 N 个、缺几个、拷不动几个」。备份目录里的 `_meta.json` 还记着
  `verify: {checked, missing, size_changed, copy_failed}`，事后可追溯。
  常见失败原因是该槽的 dsh 还在跑（锁住 `.dsh-home` 里的文件）—— 先停掉再重试。
- **失败怎么办**：备份失败/核对不过 → 该槽**不删文件也不改配置**（避免丢数据）；删文件失败 → 该槽**保留在配置里**可重试。
- **和 `uninstall-here.bat` 的关系**：同一套安全规则的两份实现
  （`dsh_uninstall_ops.py` ↔ `uninstall.ps1` 的 `Test-SafeToDelete`），回归在 `scripts/test-slot-ops.py`。
  区别：GUI 版改配置用原子写（保持中文与缩进），且**全卸完也不删 config.json**（只清空槽列表），
  所以管理器回到「零槽引导卡」而不是打不开。
- **现状**：✅ 已落地。
- **位置**：`dsh_manager.pyw`（`uninstall_versions_dialog` / `_do_uninstall`）、`dsh_uninstall_ops.py`、
  `docs/dsh管理器功能说明书.md` §7.1、`README.md` §4.7。

### Q0c-2. 把 dsh-tm 管理器删掉，各个 dsh 版本还能自己跑吗？
- **答复**：**能，而且这是设计目标**：**卸掉管理器不能影响任何 dsh 版本** —— 任何时刻，
  每个 dsh 版本都能自己单独运行；管理器只负责把这些版本管起来。
- **为什么能**：每个槽都是**自给自足**的 —— `node\`（自带运行时）、`node_modules\`
  （dsh 本体）、`.dsh-home\`（数据）、三件 bat 全在槽目录里，bat 里写的是**绝对路径**，
  不读 `config.json`、不读注册表、不依赖管理器的任何文件。
- **唯一会退化的是「停止」**：`kill-<端口>.bat` 调用管理器里的 `dsh_kill.py`。那个文件不在时，
  脚本**优雅退出**（`rc=0`）并打印：
  「管理器可能已被卸载或搬走。dsh 本身不受影响，仍然可以照常启动。」
  + 自查端口占用者的步骤（`netstat -ano` → 按 PID 结束那个 `node.exe`）。
  **不会**改成"按端口盲杀" —— 端口被别的程序占用时误杀是不可接受的。
- **端口预检同理**：预检脚本缺失时**静默跳过**，直接启动（fail-open）。
- **怎么验的**：`scripts/test-standalone.py` —— 把 bat 生成时的 `BASE_DIR` 指向一个
  **不存在的目录**（等价于管理器已删），然后用**真的 `cmd.exe` + 真的 `node.exe`** 跑：
  `dsh.bat` 拉起 node 并传参 ✓、`dsh-cli.bat` 透传参数 ✓、`kill-<port>.bat` 优雅退出 ✓。
  已注册进 `check-all.ps1` 的离线回归。
- **现状**：✅ 已落地并有回归守着。

### Q0c-3. 我想把这批版本放出来自己跑，再把管理器指到别的位置管另一批，怎么做？
- **答复**（2026-10-31 新增「移出管理」）：点「设置 → 版本管理 → **卸载 / 移出管理**」→ 选中一个槽 →
  按「**移出管理（不删文件）**」。一个一个移，全部移完之后：
  1. `config.json` 里 `versions` 空了 → **安装根目录自动解锁**
     （锁定条件就是「有槽」：`locked = bool(SLOT_KEYS)`）；
  2. 到「设置 → 目录」把安装根改到新位置（例如 `<安装根>`）；
  3. 再点「安装官方版 dsh」或「扫描已装 dsh 并纳入」，新的一批就落在新位置。
- **移出到底改了什么**：只改 `config.json`（把那条槽从 `versions` 挪到顶层 `detached`）。
  槽目录、`node_modules`、`node`、`.dsh-home`、三件 bat **一个字节都没动** ——
  回归里是逐文件比对 md5 的（`test-slot-ops.py` I3 / I13）。
- **移出后那些版本还能用吗**：能。它们就是普通的、能自己双击 `dsh.bat` 启动的 dsh 安装
  （与 Q0c-2 是同一条性质）。
- **想回头**：点「扫描已装 dsh 并纳入」，它会重新发现这个槽并原地接回（不复制）。
  **端口从槽里的 bat 读**（那是实际启动用的值）；如果那个端口已经被
  另一个槽占了，会明确警告而不是替你改。
- **为什么必须留这条记录**：换过安装根之后，旧位置的槽**不在**扫描范围里
  （`detect_existing_installs` 只扫当前 `versions_root` 和 npm 全局），没有 `detached`
  记录就再也自动发现不了它们。记录里存的是**绝对路径**，不是 `<base>` 占位符 ——
  占位符会跟着新安装根漂移，反而指错地方。
- **移出时正在运行的槽会被拒绝**：移出后管理器不再跟踪它的进程，用户就没地方点「停止」了。
  先点卡片上的「停止」再移出。（卸载可以「先杀再删」，移出什么都不动，所以只能要求先停。）
- **现状**：✅ 已落地。

### Q0d. 安装时能直接看到所有 dsh 版本吗？还要自己记版本号吗？
- **答复**：不用记了。「安装官方版 dsh」对话框会从 **npm registry** 拉取
  `@deepseek-ai/dsh` 的**全部已发布版本**（当前 40 个），按 semver 从新到旧列出，
  并标注 dist-tag（`最新` = latest、`预览` = next）与 `已弃用`。点一行即填进输入框，
  默认选中 `latest`。
- **网络不通 / 走代理**：会依次试 `registry.npmjs.org` → `registry.npmmirror.com`；
  两个都不通时列表区显示「获取失败，可手动输入版本号」，手填（含 `latest` / `next`）照常可用。
- **为什么不用 `npm view`**：pythonw 无控制台时 `npm.cmd` 会派生 node 孙进程继承管道，
  读管道可能永久阻塞（管理器会卡死在出窗口前）；直接 HTTP 拿 JSON 没这个问题。
- **现状**：✅ 已落地（`dsh_registry.py` + `_build_version_picker`）。
- **位置**：`dsh_registry.py`、`dsh_manager.pyw`（`_build_version_picker` / `install_official_version`）、
  `scripts/test-slot-ops.py`（解析与排序回归）。

### Q0e. 新装的槽里没有 `node\` 目录、`dsh.bat` 里写的是裸 `"node"`，正常吗？
- **答复**：**不正常，是 2026-10-29 修掉的一个缺陷**。`config.json` 里 `node_exe` 存的是可移植
  占位符（`<base>/dsh-versions/dshV1/node/node.exe`），而装新槽时挑 node 的那个函数直接拿占位符
  去 `os.path.isfile()` —— 恒为 False，于是**每个新槽都退回系统 node**，目录里自然没有 `node\`。
- **影响**：① 违反「每槽自带 node」的隔离设计，装依赖时用的可能是系统 node（ABI 不同会崩
  `node-pty` 这类原生模块）；② `dsh.bat` 里写裸 `"node"`，依赖 PATH 上有 node —— 系统 node 被卸载
  或 PATH 变动后该槽直接起不来。
- **已修**：`_pick_node_exe(existing, base, home)` 现在会先展开 `<base>` / `<home>` / `<self>` /
  `<npm_global>` 再判断文件存在性；回归在 `scripts/test-install-ops.py`（「借 node 运行时」一节）。
- **已经装歪的槽怎么办**：把任一自带 node 的槽的 `node\` 复制过去，再把 `config.json` 里该槽的
  `node_exe` 指到 `<槽目录>/node/node.exe`，最后让管理器重新生成该槽的 `dsh.bat`（换一次版本即可）。
  只想先用起来的话，系统 PATH 上有 node 就能跑，但别指望 ABI 隔离。

### Q0e-2. 我装 v1，为什么目录叫 `dshV1-2` 而不是 `dshV1`？
- **答复**：因为 `dshV1` **这个名字已经被占着**了 —— 装槽时会先找一个可用目录名
  （`unique_dir`），同名就让位成 `dshV1-2`。
- **占着它的是什么**：多半是**上次卸载残留的空壳**。卸载最后一步是 `os.rmdir(槽根)`，
  而 Windows 刚删完几万个文件时，目录常被索引器 / 杀软 / 资源管理器短暂占住，`rmdir`
  失败 → 留下一个只剩空 `.dsh-home` 的目录（**零文件**）。它不是数据，但确实占了名字。
- **2026-10-30 已修**：
  1. 装槽前先判断目标名是不是"零文件的空壳"，是就清掉**复用原名**（`_reuse_empty_shell`），
     安装提示里会写「`dshV1` 是上次卸载残留的空目录…已清掉并复用这个槽名」；
     判定刻意保守 —— 里面只要有一个文件或一个 junction 就不算空壳，绝不动。
  2. 卸载删槽根改成**重试 3 次**（每次间隔 0.4 s），并在进度窗里显式提示失败原因。
  3. **装失败当场收回残件**（`_drop_partial_install`）—— 见下一条，这才是 `-2` 的主要产地。
- **第二个来源（比空壳更常见）：装失败 → 点重试**。`npm install` 失败时目录里已经有
  `npm init -y` 生成的 `package.json`（有时还有半截 `node_modules`），它**有文件**，
  所以不算"空壳"，`_reuse_empty_shell` 不会复用 → 重试就让位成 `dshV1-2`，再失败就 `-3`。
  现在失败路径会当场把本次新建的目录整个收回、并把槽从 `config.json` 撤掉（状态退回
  安装前），失败说明里直接写「本次未完成的目录已清理（槽名 `dshV1` 已还回来），
  直接重试即可，不会再多出一个 `dshV1-2`」。
  收回有两条安全前提，缺一不动手：**没装成**（`bin.js` 不存在）+ **`.dsh-home` 零文件**
  （有用户数据就绝不删）。
- **怎么知道现在还有没有空壳**：管理器启动日志里会有一行
  `[清理] 发现空壳目录（没有任何文件、也不在 config 里）：dshV1`，并给出完整路径。
  它**只报不删** —— 那是你主目录下的东西，管理器不替你做删除决定。
- **已经被装成 `dshV1-2` 了怎么办**：两种都行 —— ① 在管理器里卸掉该槽再装一次
  （现在会拿回 `dshV1`）；② 手工把目录改名回 `dshV1`，再把 `config.json` 里该槽的
  `label` / `node_exe` / `bin_js` / `dsh_home` / `temp_dir` 里的 `dshV1-2` 全改成 `dshV1`，
  然后点「生成启动/kill/CLI bat」重新生成三件 bat（bat 里写死了绝对路径）。
  **改完必须重启管理器**，否则界面用的还是内存里的旧路径。

### Q0f. 管理器怎么"纳入"本机已经装好的 dsh？会不会把坏的一起收进来？
- **首次启动**：扫一遍本机管理范围外的 dsh，弹一个**勾选列表**（不是"是/否"一刀切）。
  每一项都先做体检，把结果显示出来：
  - 版本号（读 `@deepseek-ai/dsh/package.json`，不信 `label`）
  - 关键组件：`lib/bin.js` 入口、`package.json`、依赖项数（少了几个）
  - 旧数据目录（有没有 `.dsh-home` / `~/.dsh`）
- **体检不过的不让勾**（灰掉并写明原因）：缺 `bin.js`、缺 `package.json`、`lib/` 是空壳、
  声明的依赖找不到、根本不是 dsh 目录 —— 这些复制过去只会得到一个"看着正常、一启动就炸"的槽。
- **纳入过程**（任一步失败即中止，原安装一个字节都不动）：
  1. 备份原用户数据目录（`.dsh-home` 或全局的 `~/.dsh`）→ **备份失败就中止**
  2. 复制 `node_modules` + 复制一份自带 node 运行时
  3. 校验复制结果（版本号必须与体检时一致、`bin.js` 必须在），不一致就清理掉重来
  4. 把第 1 步的备份**复制**进新槽的 `.dsh-home`（所以你的会话还在；原目录没动）
  5. 重建插件链接（见下一条）
  6. 写 `config.json`（`<base>` 占位符）、生成三件 bat、再对一遍"槽的形状"
- **拷什么、不拷什么**（一句话：拷的是**整个程序目录**，不是只拷数据）：
  - **整个 `node_modules`**（含 `@deepseek-ai/dsh` 与全部依赖，几百 MB）—— 复制进新槽，
    原安装保持不动。所以纳入后有两份独立的程序，以后各升各的。
  - **一份自带 node 运行时**（`node/node.exe`）—— 因为 `node-pty` 这类原生模块按 ABI 编译，
    换了 node 版本会直接崩。
  - **`.dsh-home` 的全部内容**：会话 / 设置 / 凭据 / 插件配置（profiles）。
  - **插件本体不复制**：插件挂在 `.dsh-home/profiles/<profile>/node_modules/<插件>`，
    那是一个 **junction（目录链接）**，不是副本。备份与复制都**跳过链接本身**，复制完再
    按原样重建（2026-10-30 改，见下条）。
- **插件会不会丢**（2026-10-30 修的真缺陷）：原来 `backup_dsh_home` 用 `shutil.copytree`，
  它会**跟进 junction** 把插件内容整份复制 —— 487 MB 的数据目录变成 942 MB / 6 万文件 /
  14 分钟，而且复制出来的是**副本**不是链接（以后升级插件两边各走各的）。
  现在改成「跳过链接 → 复制完重建」：
  - 链接指向**旧安装目录**里的 `node_modules` → 自动**改指新槽**（插件照旧生效）
  - 链接指向**槽外**（你自己的插件仓库 / 全局 npm）→ 原样指回去
  - 目标已经不存在 → 不建，并在结果里提示「M 个链接的目标已不存在，插件可能要在管理器里重装」
- **原安装残缺不全怎么办**：体检会**直接拦住**，不让勾（灰掉并写原因）。判据是
  `package.json` 有没有、`version` 是不是官方形态、`lib/bin.js` 在不在、`lib/` 里有没有 `.js`、
  声明的依赖是不是都在。**宁可拒绝也不收**：半装的目录复制过去只会得到一个
  "看着正常、一启动就炸"的槽，那比直接报错更难排查。建议改用「安装官方版 dsh」重装一份。
  唯一的例外是**依赖缺失但目录本身完整**（比如手动删过某个依赖包）—— 也会被拦，
  因为 `node_modules` 里缺东西启动必崩。
- **不想纳入某个版本**：不勾它、或直接点「取消」就行 —— 什么都不记。
  下次再点「设置 → 版本管理 → **扫描已装 dsh 并纳入**」，它照样会重新列出来（每次都重查磁盘）。
- **已经纳入的不再出现**：判定依据是该安装目录已在 `config.json` 的版本根之内。
- **位置**：`dsh_manager.pyw`（`scan_and_offer_adopt` / `_adopt_picker_dialog`）、
  `dsh_adopt.inspect_adopt_source`（体检）、`dsh_install_ops.adopt_existing`（执行）、
  `scripts/test-adopt-logic.py`（体检 9 项断言）。

### Q0g. 能不能一次装好几个版本？卸载能一次卸好几个吗？
- **安装：能。** 点「安装官方版 dsh」，在版本列表里 **Ctrl 点选多个 / Shift 连选**，
  或直接在输入框里写 `0.2.0-rc.2, 0.2.1-alpha.2`（逗号、空格、换行都行）。
  程序按你写的顺序**逐个**装，每个装进当时的下一个空槽；**中途某个失败不会中断后面的**，
  全部结束后只重启一次管理器，最后一次性列出「✓ 哪个成功 / ✗ 哪个失败、为什么」。
  失败的版本直接再点一次「安装官方版 dsh」重试即可。
  一次最多能填「上限 − 当前槽数」个（上限 6），填多了会先提示，不会装到一半才发现装不下。
- **卸载：不能，一次一个。** 这是刻意的：卸载会删几百 MB 并改 `config.json`，
  多选时很容易连带勾上另一个槽，而确认框里的摘要根本看不出差别（`dshV1` 与 `dshV1-2`
  只差一个后缀）。卸完一个再卸下一个，出错也容易定位。

### Q0g-2. 界面能切成英文吗？切换要重启吗？
- **能，而且不用重启。** 设置 → 界面 → 「界面语言」→ English，**立即生效**。
  配置存在 `config.json` 的 `ui.lang`（缺省 `zh`，老配置无感）。
- 英文模式下点「使用说明」会打开 `docs/user-guide.en.md`（英文版），找不到才退回中文版。
- 翻译层是「**中文原文当 key**」：`lang/en.json` 里查得到就显示英文，查不到原样返回中文。
  所以任何一条漏翻最多是那一句显示中文，**不会出现空白或 `ui.install.title` 这种 key 名**。
- 哪些东西**故意不翻**：`dsh备份` 目录名（磁盘上就叫这个）、日志分级关键词
  （`失败`/`错误`/`异常`，用来判断日志级别）、`纳入`/`运行中` 等内部枚举值 ——
  翻了会导致目录改名或判断失效。

### Q0h. 端口是固定的吗？会不会跟别的程序撞？
- **不固定，取「不冲突的任意一个」。** 规则是两段式：
  1. 先按槽序取首选端口：第 1 槽 4080、第 2 槽 5080、第 3 槽 6080、第 4 槽 7080、第 5 槽 8080。
     **不特意避开 6080 / 8080** —— 唯一判据是「这个端口此刻有没有被占」；
     首选被占就在这段里往后找最近的空闲端口（最多 200 个）；
  2. 这一段全被占（或全在 config 里）就退到 **20000–29999** 里找一个空的。
  判据始终两条：**不在 `config.json` 已登记的端口里** + **真实 bind 探测没被占**
  （所以不会跟别的软件抢端口，也不会两个槽撞车）。两段都找不到才报错。
- 想固定用某个端口：直接在 `config.json` 里改该槽的 `port`（并同步 `extra_args` 里的
  `--port`），然后点「生成启动/kill/CLI bat」重新生成 bat —— bat 里写死了端口。

### Q0i. 界面上一排槽太挤，只想看其中两个 / 想调左右顺序，怎么办？
标题栏点「**设置**」（2026-10-31 新增）。里面三件事一起做：

| 想做的事 | 怎么操作 |
|---|---|
| 只看某几个槽 | 在列表里**双击**（或按空格）把不要的取消勾选 —— `[✓]` 是显示、`[  ]` 是隐藏 |
| 调左右顺序 | **最省事：直接在主窗口把卡片拖过去**（手机手感）—— 按住卡片**任意位置**往外拖，卡片会浮起来跟着走、其它卡片实时让位，松手落下即生效、不用开设置。设置里也可以点中一行用「上移 ↑ / 下移 ↓」，或者直接拖列表里的行 |
| 最多显示几个 | 「设置 → 界面」里的「最多同时显示 [N] 个槽」。勾选数超过它时只显示靠前的几个（会提示你） |

点「保存」后**立即生效，不用重启管理器**。设置存在 `config.json` 的顶层 `ui` 段：

```json
"ui": { "max_visible": 4, "order": ["v2","v1","v3","v4"], "visible": ["v2","v1","v3"] }
```

- **隐藏 ≠ 卸载。** 隐藏只是不画那张卡片；它的 dsh 进程照跑、端口照占、数据目录照在，
  「卸载」「杀全部」的名单也不受影响 —— 所以调布局**不可能丢东西**。
  想停掉一个隐藏了的槽？先把它显示出来，再点「停止」（或者在任务管理器里结束那个 node）。
- 至少会留一个显示（全关会被拦），因为空白界面容易被当成"程序坏了"。
- 隐藏后**窗口宽度会跟着变窄**（按显示槽数算），不会留下一大片空白。
- 装新版本时会自动出现在**末尾**（`ui.order` 是旧快照，代码会把没记过的槽接在后面），
  不会出现「装了却看不见」。
- 想把设置全清掉：删掉 `config.json` 里那个 `ui` 段即可，界面回到「全显示、按 config 顺序」。

**关于拖拽的几个细节**（2026-10-31）：

- **抓哪儿都能拖**：卡片边框、标题、状态行，**连按钮上也能拖**。鼠标移到这些地方会变成四向箭头 —— 卡片上没有任何文字提示，光标就是唯一信号。
- 按钮上「按一下」还是点按钮，「按住往外拖」才变成拖卡片 —— 位移不到 8 px 一律当点击，
  拖过了则这次点击会被吞掉，**不会出现「想拖卡片结果顺手启动了一个版本」**。
- 拖动时卡片会浮起来（边框变色 + 右下角一块灰影子），其它卡片实时让位，空出它将要落下的位置。
- 拖动过程中鼠标移到别的卡片、甚至移到日志区都没关系 —— motion 与松手都挂在顶层窗口上兜底，
  一定收得到（不会出现「看着在动、松手却没记住」）。
- 位移小于 6 px 不算拖 —— 手抖一下不会把顺序弄乱；拖回原位也不会写盘。
- 只重排**当前显示中**的那几张卡片。被隐藏的槽在完整顺序里**原地不动**，
  以后重新显示时位置不会跑。
- 松手才写 `config.json`（拖动过程中只是画面上移动）；写盘失败会立刻把界面恢复成
  磁盘上的顺序，不会出现「界面一套、配置另一套」。

### Q1. 双击桌面 `dsh-manager.lnk` 没有任何反应 / 窗口不出现？
- **答复**：根因有两个，按概率从高到低：
  1. **缺 `config.json`**——仓库只提供 `config/config.example.json`（用户改过的文件不入库）。老版本管理器会 `_fatal` 弹个错就退；现在的 `dsh_manager.pyw` 会在检测到 `config.json` 缺失时**自动从 example 复制一份**再启动，所以这条对当前代码已不构成问题。
  2. **`.pyw` 关联到无 tkinter 的 Python**——`.pyw` 默认识别是 `pyw.exe`，它可能选到某个无 tkinter 的 Python（例如某个工具自带的精简版 3.13）→ `import tkinter` 失败。
     **2026-10-31 起自愈**：这种情况下管理器**不再弹「请重装 Python」**，而是自动用包内的
     `runtime\python\pythonw.exe` 重开自己（三道闸防死循环：环境变量 `DSH_MANAGER_TK_RELAUNCH=1`、
     包内解释器必须存在、且不能就是当前这个）。只有在**包内解释器也缺 tkinter**时才会弹框，
     那时第一条建议是「双击桌面快捷方式 / `start-manager.bat`」，重装 Python 退到最后一条。
     回归：`scripts/test-tk-selfheal.py`。
  3. **更隐蔽的坑**：9/8 装了微软商店的「Python Manager」3.14，它注册的 App Execution Alias 会让 `shutil.which("pythonw")` 命中 `WindowsApps` 下的壳，build_lnk.py 已显式排除该路径。
- **现状**：✅ 已落地（`dsh_manager.pyw` 自动生成 config；`build_lnk.py` 排除 WindowsApps；`README.md` §七 故障排查表已收录）。
- **位置**：`README.md` §三。

### Q2. 为什么仓库里没有「一键安装」脚本？
- **答复**：故意的。仓库只负责**打开管理器**（`start-manager.bat`），「装哪个版本、装到哪、占哪个端口」全部由界面里的「安装官方版 dsh」完成——那条路径按 `config.json` 的槽位走，支持 1~6 槽、自动分配端口、失败当场收回半成品。

- **想补依赖**：自己装 Python（勾 tcl/tk）与 Node ≥ 22.19 即可，本仓库不依赖 winget。

## 二、跨机器 / 便携

### Q4. 把仓库拷到另一台电脑，双击就能用吗？
- **答复**：分两种情况。
  - **便携包（别人装好后拷给你的整个目录）**：可以。目录里自带便携 Python（含 tkinter）、node 运行时和现成的 dsh 依赖树，双击 `start-manager.bat` 即可。
  - **仓库源码（git clone / zip）**：**不能直接用**。仓库里只有源码 + 配置模板 + 脚本，**不含** `runtime\`（便携 Python 与 node，约 200 MB，被 `.gitignore` 排除），也没有任何 dsh 版本、没有 `config.json`（gitignored）、没有桌面 `.lnk`。要先按 `README.md` §二 准备好 Python（带 tkinter）和 Node，再启动管理器装版本。
- **想让目标机什么都不装**：把**整个目录**（连被 `.gitignore` 排除的 `runtime\` 一起）拷过去即可，见 Q5b。
### Q5. `config.json` 里的 `<base>` / `<home>` / `<self>` / `<npm_global>` 是什么？
- **答复**：占位符，写一次到处可搬。迁机器通常只改 `install_base`。
  - `<base>` = `install_base` 的解析值（安装根目录）；
  - `<home>` = 当前用户主目录；
  - `<self>` = 管理器自身所在目录；
  - `<npm_global>` = 运行时 `npm root -g` 的输出（用于定位 npm 全局装的 dsh）。
- **注意**：占位符只有管理器认。给 `cmd.exe` 读的 `.bat` 里必须已经是**展开后的绝对路径**（管理器生成时就会展开）。
### Q5b. 另一台电脑（Win10 家庭版 64 位）**不联网、不装 node/Python**，能直接跑多个版本吗？
- **答复**：**能，把整个目录拷过去**。在一台已经装好的机器上，关掉管理器，把整个项目目录
  （**连 `runtime\` 一起**，它只是被 `.gitignore` 排除、不进 git，复制时会一起带走）
  用 U 盘 / 局域网拷到目标机，双击 `start-manager.bat` 即可。
  目录里已经有便携 Python（含 tkinter）、node 运行时，以及各槽的**完整依赖树**，
  所以目标机既不用预装任何东西，也不用下载任何依赖。
- **为什么不走 `npm install --offline`**：实测用预热好的 npm 缓存离线装**一版就要 18 分钟**
  （还得先联网预热 170MB 缓存，且缓存缺 metadata 就 `ENOTCACHED`）。直接带现成依赖树是秒级。
- **关键依据**：`node-pty` 是 N-API 预编译二进制（含 `napi_register_module_v1`），
  ABI 跨 node 版本稳定，所以带过去的二进制可以直接用，目标机无需编译。
- **位置**：`README.md` §4.12。

### Q5c. 双击 `.bat` 中文全是乱码（Win10 家庭版）？
- **答复**：这是 **.bat 文件编码**问题，已修。根因与修复：
  - cmd.exe 按 **ANSI 代码页（中文 Windows = GBK）** 逐字节解析 `.bat` 内容；
    仓库里的 bat 原先是 **UTF-8 无 BOM**，中文在 cmd 眼里就是非法字节 → 乱码。
  - bat 里那行 `chcp 65001` **救不了**：它只能改变「后续输出」的代码页，
    改变不了 cmd 已经按 GBK 解析脚本内容的事实；而且切页后 PowerShell 回显到 cmd 的
    UTF-8 字节又被按 GBK 解释 → **第二重乱码**。
  - 修复：仓库里所有 bat 统一存成 **GBK(cp936)** + **删掉 `chcp` 行** + 统一 CRLF，读写两端代码页一致。
- **防回归**：`python scripts\fix-bat-encoding.py --check`（只检查不写回）。
  改完 bat 后跑一次，确保「非 GBK 字符 = 0」。
- **另一个盲区（2026-10-15 补）**：上面这条只扫**仓库内**的 bat；管理器还会往**每个版本槽目录**
  生成三份 bat（`dsh.bat` / `kill-<port>.bat` / `dsh-cli.bat`），它们不在仓库里、扫不到，
  而恰恰是用户会双击的文件。所以加了 `--slots` 模式（从 `config.json` 的 `bin_js` 反推槽根）：
  `python scripts\fix-bat-encoding.py --slots --check`；`check-all.ps1` 现在两项都跑。
  生成器本身已改成 GBK，`--slots` 用来守住存量文件。详见 Q0a。
- **现状**：✅ 已修复（仓库里所有 `.bat`，回归 `scripts/test-bat-text.py`）。
- **注意**：用记事本改 bat 后保存时，编码要选 **ANSI**；存成 UTF-8 会复发。

### Q6. 怎么把整套东西迁到 D 盘 / 另一台机器？
- **答复**：
  - **同机换路径**（2026-10-31 起改成「装之前就问」）：位置在**第一次安装/纳入时确定**，
    之后锁定。想换：① 先把 `dsh-versions` 整个目录复制到新盘 ② **把所有版本卸载干净**
    （卸载会先备份用户数据）③ 重新安装 —— 那时会重新弹「把 dsh 版本放在哪」。
    为什么不能中途改：一次装到两个地方就得同时管两处，备份目录、临时目录、空壳扫描、
    新建槽的落点全部分叉。设置里的「安装根目录」有槽时是只读的。
  - **命令行等价**：`scripts\uninstall.ps1 -Target all` 卸干净 → 改「设置 → 目录」的安装根 → 重新装。
  - **跨机迁移**：整包拷过去（或先 clone 再补 `runtime\`），在管理器里重新装 / 纳入；旧机的用户数据从 `<安装根>\dsh备份\<槽>-userdata-*\` 取回。
- **现状**：✅ 已落地。

### Q6a. 装了好几个版本，C 盘满了 / 想换到别的盘，需要全部卸载吗？
- **答复**：**不需要**。用「设置 → 目录 → 移动安装根目录…」整体搬过去就行。
  - 过程：**复制 → 校验（文件数 + 字节数）→ 改配置 → 删旧位置**。任何一步失败都保留旧位置、
    不动配置；目标已有同名目录一律中止，绝不覆盖。
  - 搬完会自动按新位置**重写三件 bat**（bat 里是绝对路径），双击 `dsh.bat` 照样能启动。
  - 两个前提：① **先把所有版本停止**（运行中的程序占着文件，复制会失败）；
    ② 目标盘空间要够 —— 管理器会**事前算**（含 5% + 200MB 余量）并告诉你"需要多少 / 可用多少"，
    不会拷到一半才报盘满。
  - 不想搬、只想让**以后新装的**放到别的盘？那就得先把现有槽全部「移出管理」（不是卸载，
    磁盘一个字节都不动），锁解开后改安装根，再点「扫描已装 dsh 并纳入」把旧槽接回来。
- **现状**：✅ 已落地（`dsh_move.py` + 离线回归 `test-move.py`）。

## 三、安装

### Q7. 装一个 dsh 版本到底做了什么？
- **答复**：全部在管理器界面里，点「安装官方版 dsh」→ 选版本（或手填版本号）。管理器依次完成：
  1. **规划槽位**：找下一个空槽键（`v1`~`v6`）、按槽序挑端口（4080 / 5080 / 6080 / 7080 / 8080，不特意避开 6080/8080）。
  2. **装依赖**：用**该槽自己的 node** 跑 `npm init -y` + `npm install @deepseek-ai/dsh@<版本>`；先 `npm view` 预检选源，网络错误自动换镜像重试一次。
  3. **写配置**：登记到 `config.json`（路径一律写成 `<base>` 占位符）。
  4. **生成三件 bat**：`dsh.bat` / `dsh-cli.bat` / `kill-<port>.bat`，全是展开后的绝对路径。
  5. **复核槽形状**：自带 node、`bin.js`、占位符、独立 temp、三件 bat 缺一不可；不过就当场收回半成品。
- **为什么没有命令行等价物**：装槽要处理 npm 选源、失败回滚、端口探测、槽形态复核——这些逻辑只有一份实现（`dsh_install_ops.py`），GUI 直接调它。仓库里再放一个「一键装」脚本，等于把同一件事写两遍，早晚不一致。
### Q8. 怎么自定义安装路径 / 版本号 / node？
- **装在哪**：**第一次安装/纳入时**管理器会弹「把 dsh 版本放在哪」，选好就锁定（缺省 = 用户主目录）。中途要换得先把槽全部卸载或移出。
- **装哪个版本**：管理器「安装官方版 dsh」里从列表选，或直接手填版本号 —— 不用改任何文件。
- **想一次性装多个**：「安装官方版 dsh」支持一次勾选多个版本，管理器会排成队列逐个装进空槽，最后只重启一次界面。
- **换浏览器 / 端口 / 数据目录**：浏览器在管理器「设置」里选；端口与 `dsh_home` 属于 `config.json` 字段，手改后要点「生成启动/kill/CLI bat」并重启管理器。详见 [`dsh管理器使用说明.md`](dsh管理器使用说明.md) §8。
### Q9. 公司电脑禁用了 winget 怎么办？
- **答复**：**不需要 winget**。本仓库不调用它。自己装 Python（**必须带 tkinter**，安装时勾 tcl/tk）与 Node ≥ 22.19 到 PATH，然后双击 `start-manager.bat` 即可。
- **现状**：✅ 设计如此（管理器只用标准库 + 系统自带的 node/python）。

### Q10. 中途失败了再点一次会怎样？
- **答复**：**失败会当场收回半成品**（`_drop_partial_install` + `_unregister_slot`，前提是 `bin.js` 不存在且 `.dsh-home` 零文件），所以直接重连后重新点「安装官方版 dsh」即可，不用手工清目录。
- **例外**：目录里若留下 `dshV1-2` 这种零文件空壳（卸载时 `rmdir` 失败留下的），下次装槽会**复用它**；启动时发现的历史空壳只在日志里报出来，**只报不删**。

## 四、平台 / 兼容性

### Q17. 仓库适用操作系统还是 Windows 吧？
- **答复**：**是，且仅限 Windows 10/11**。判断依据（代码里实际用的，不是猜的）：
  - 入口脚本是 `.bat` 和 `.ps1`；
  - 桌面快捷方式是按 [MS-SHLLINK] 手工构造的 `.lnk`；
  - 装依赖用 `winget`（Win10+ 才有）；
  - 进程/端口管理用 `taskkill` / `netstat`；
  - 管理器依赖 Windows 版 `pythonw.exe` + `tkinter`。
- **macOS / Linux 怎么办**：当前**不支持**。要跨平台需要重写：安装层换成各自的 shell + 包管理器；快捷方式换成 macOS 的 `.command`/`.app` 或 Linux 的 `.desktop`；`.lnk` 二进制构造整段换掉。**工程量较大**，本项目未做。
- **现状**：❌ 跨平台未实现（仅 Windows）。

### Q18. 需要管理员权限吗？
- **答复**：**完全不需要**。安装 / 启动 / 停止 / 打开浏览器 / 换版本 / 看状态 / 生成 bat / 卸载，
  全部在普通用户权限下完成。管理器可以放在任意用户目录，装槽写的是用户目录下的文件，
  winget 也默认 `--scope user`。
- **为什么「停止」不需要提权**：dsh 进程是**管理器自己 `Popen` 出来的子进程**。
  Windows 上结束自己起的子进程**天生就有权限**，与是否提权无关 —— 实测
  `OpenProcess(PROCESS_TERMINATE)` 对同用户进程直接成功（`lastErr=0`）。
- **提权唯一可能相关的场景**：结束**别的软件**的进程。而管理器**本来就不做这件事**
  （签名门控：只杀命令行/端口能认出来的 dsh，端口被非 dsh 占用时只告警不杀）。
- **受影响的是什么**：只有「端口被谁占用」弹框说不出程序名/命令行这一条**边缘诊断**
  （`Get-CimInstance` / `tasklist` 在普通权限下可能报「拒绝访问」），已降级为
  `Get-Process`，主流程零影响。
- **启动时不再弹权限提示**（2026-10-31 起）：能力状态只写日志。若真的点「停止」没反应，
  更可能是**安全软件拦截**，而不是权限不足 —— 那时才会给出针对性提示。

### Q18b. 以前启动时那个「建议以管理员身份运行」的弹框是什么？

### Q19. 怎么确认安装成功？

### Q19b. 有没有一条命令能一次看清所有槽和配置有没有问题？
- **答复**：有，用 `python dsh-tm.py doctor --json`。**只读**，不写盘、不启停进程、不修文件；一次把「配置校验 + 槽体检 + 槽形状复核」合成一份结论。
  - 每条问题带固定英文 `code` / `source` / `action`（`config` / `health` / `shape` 三个来源），每个槽给 `level`、`issues[]` 和 `actions[]`；顶层有 `level`、`summary`、`config_valid`。

  - 所有 `--json` 结果都带 `config_problems[]`。比如 `port` 和 `extra_args` 里的 `--port` 不一致，这里会点名并给出 `expected` / `actual`；`start` / `stop` 会拒绝执行这个槽（`config_port_invalid`），不会拿错端口去启停进程。
  - 有「错误」时退出码为 `1`，方便脚本/CI 判断。完整字段和错误码见 [`agent-api.md`](agent-api.md)（中英双语）。

### Q20. 出现 EADDRINUSE / 端口被占怎么清理？
- **答复**：
  1. 管理器点标题栏「**全部停止**」（或 CLI `kill-stray --yes`，只杀认得出的 dsh）；
  2. 或手动：`netstat -ano | findstr :<端口>` → 拿 PID → `taskkill /PID <pid> /F`。
- **如果占用者是别的程序**：管理器会**拒绝**杀它，只弹框告诉你是谁。这时要么关掉那个程序，要么改该槽的 `port`（记得同步 `extra_args` 里的 `--port`，再点一次「生成启动/kill/CLI bat」）。
- **强杀后的孤儿锁**：dsh 被 `taskkill /F` 干掉会留下 `.credentials.yaml.lock`。管理器启动时会自动清理（确认 PID 已死、或活着但不是本槽才删）。
### Q21. 浏览器 401 怎么办？（新版 dsh 的入口 token；手动打开什么情况能开？）
- **答复**：**新版 dsh（0.1.5 起）**的网页版带入口 token 鉴权：用带 token 的 URL 访问一次 → 浏览器种 30 天有效 cookie（绑定该端口）。`0.1.0-rc.8` **没有** token，裸地址直接开。
  - ⚠️ 先记住：**是否需要 token 是 dsh 版本决定的，与是否隔离无关**。所以别再说"v2 才有 401"——把 v1 槽换到 0.1.5+，v1 也会要 token。
  - ✅ 用管理器「打开浏览器」→ 一定可以（自动带完整入口 URL）；
  - ✅ 用管理器「**复制入口 URL**」→ 拿到带 token 的完整 URL，粘到任意浏览器 / 别的机器都能开；
  - ✅ **同一浏览器**之前成功开过该端口，30 天内手动输 `127.0.0.1:<端口>` → cookie 还在，能开；
  - ❌ 把 A 槽的地址改个端口就粘到**从没开过 B 槽的浏览器** → 401（既无 token 也无 cookie）。
  **日志里的 token 已经自动打码**，所以不要再从 `dsh-manager.log` 里找完整 URL（旧做法已失效），改用「复制入口 URL」按钮。
  没装默认配的 Edge（或 Chrome）时，管理器会自动改用**系统默认浏览器**打开，只要机器上有能开网页的浏览器就不会卡在这（浏览器怎么配见 [`dsh管理器使用说明.md`](dsh管理器使用说明.md) §4.3）。
- **现状**：✅ 已落地（`dsh_manager.pyw` 的 `_scan_slot` 按槽抓入口 URL 并就地打码；`_scrub_existing_log` 启动时清理历史 token；cookie 有效期 30 天为 dsh 默认 `cookieMaxAgeDays`）。

## 七、精准杀 node 详解（`dsh_kill.py`）

### 三条判据

| 说法 | 对不对 | 精确说法 |
|---|---|---|
| 「只要用了这个端口，单个『停止』就能杀」 | ⚠️ 部分对 | 「停止」按 **签名 + 端口** 杀，不是"见端口就杀"。它杀的是**该槽**的 dsh 进程（不管是不是管理器启动的），但端口被**非 dsh** 进程占用时**拒绝杀**并告警 |
| 「『杀全部』能杀掉所有 dsh node，即使端口不对」 | ✅ 对 | 「杀全部」枚举**所有 `node.exe`**，按泛签名（命令行含 `@deepseek-ai/dsh`）匹配，杀掉**所有** dsh 相关 node 进程，**不限端口**。同样不碰其它应用的 node |
| 「换个端口就杀不到了」 | ✅ 对 | 单槽「停止」的端口来自 `config.json`。你手动改了 `--port` 就不在它的视野里 —— 用「杀全部」 |

### 什么是"签名"

杀进程前先拿到每个 `node.exe` 的**完整命令行**，看它是否命中签名：

- **单槽签名**：命令行里含**该槽 `bin.js` 的绝对路径**（如 `<安装根>\dsh-versions\dshV1\node_modules\@deepseek-ai\dsh\lib\bin.js`）。
- **泛签名**：命令行里含 `@deepseek-ai/dsh`（用于「杀全部」的槽外兜底）。

`bin.js` 绝对路径**每槽唯一**，所以天然能区分"这个 node 是这个槽的、还是别的槽的、还是别的软件"。签名由管理器按 `config.json` **动态构造**，换机器、换槽位自动跟着变。

> **历史坑（值得记住）**：早期实现还额外要求命令行出现字面量 `--port <端口>`。那会漏掉「裸敲 `dsh web`、手写启动器」起的**同版本**进程 —— 界面显示「外部占用，点『杀全部』清理」，而「杀全部」用的是同一套签名、**同样清不掉**，提示与行为自相矛盾。现在已去掉这个附加条件。

### 各按钮的精确行为

| 按钮 | 实际动作 | 会不会误杀 |
|---|---|---|
| 单个「停止」 | 杀该槽签名命中的 node + 该槽端口上的 dsh 孤儿 + 本管理器跟踪的 PID | 不会 —— 签名不含该槽的一律拒绝 |
| 「杀全部」 | 对每个槽跑一遍按签名清理，再扫端口做最终守卫 | 不会 —— 最终守卫对仍占端口的**非 dsh 进程**只告警不碰 |

### 多级回退（为什么不会"杀不动"）

对每个目标 PID 依次尝试，每一步都验证"还活着吗"：

```
1. taskkill /PID <pid> /F            # 先只杀主进程，尽量不波及子进程
2. taskkill /PID <pid> /T /F         # 连带子进程（进程树）
3. TerminateProcess（原生 Win32 API） # 兜底，绕过 taskkill 偶发的静默失败
```

### 拒绝误杀的守卫（核心安全线）

- 枚举端口占用者时，若某进程占了该槽的端口**但命令行不匹配任何 dsh 签名**，**绝不 kill**，只写日志并弹框说明「端口被非 dsh 程序占用，请人工确认」。
- 所以即使你机器上有别的软件也用 node、甚至碰巧用了同一个端口，管理器也不会误伤它。
- **代价**：这种情况该槽起不来，需要你自己关掉那个程序，或给这个槽换一个端口。
