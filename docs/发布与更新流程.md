# 发布与更新流程

> **这份文档给谁**：任何要**发新版本**的人（含未来的自己、接手的人、AI agent）。
>
> **解决什么问题**：把"发版前该查什么、怎么查、查到什么算过"固定下来，避免每次靠记忆、每次重新踩坑。
>
> **怎么用**：发版前从 §1 顺序走一遍；新增功能后回来看 §5 要不要补检查项。

---

## 0. 一句话

> **发版不是"代码写完推上去"，而是"站在首次使用者视角，把该露的露出来、该藏的藏干净"。**

---

## 1. 发版前必跑的四道检查

### 1.1 隐私与安全扫描（最高优先级，不可跳过）

**为什么必须机器扫而不是肉眼看**：人眼会漏掉第 37 个文件里的一个用户名；脚本不会。

```bash
# ① 真实用户名 / 主机名（把 <你的用户名> 换成实际的，注意排除 arnen7000 这类正式名）
git ls-files -z | xargs -0 grep -nIE '<你的用户名>|RENCY_B' || echo "OK"

# ② 本机绝对路径（D:\xxx、C:\Users\真名\...）
git ls-files -z | xargs -0 grep -nIE '[A-Za-z]:[\\/](Users[\\/][A-Za-z0-9_.-]+|DSH|Programs)' \
  | grep -viE '<|xxx|用户|you|name|\.\.\.' || echo "OK"

# ③ token / key / 密码
git ls-files -z | xargs -0 grep -nIE 'token=[A-Za-z0-9]{12,}|sk-[A-Za-z0-9]{16,}|password\s*[=:]' || echo "OK"

# ④ 敏感文件名
git ls-files | grep -iE 'credential|secret|password|\.env$|\.pem$|\.key$' || echo "OK"
```

**判定**：四条全 `OK` 才算过。

**这些必须已被 `.gitignore` 覆盖**（漏一个就会把用户数据推上去）：

```
config.json    dsh-manager.log    .credentials.yaml    temp/    __pycache__/
dsh备份/       runtime/           dsh-versions/        *.bak-*
```

### 1.2 最小必要原则

> **仓库里每一个文件都要能回答"新用户为什么需要它"。**

判断标准：

| 该删 | 该留 |
|---|---|
| 一次性开发工具（图标生成、编码修复脚本） | 用户会用到的入口脚本 |
| 只被已删文件引用的资源 | 被代码/文档实际引用的资源 |
| 描述"某台机器现状"的文档 | 描述"这个软件怎么用"的文档 |
| 已被新流程取代的旧脚本 | 仍在被调用的脚本 |

**删除前必查引用**：

```bash
git grep -l '<文件名>' | grep -v '<文件名>本身'
```

有引用就不能直接删——要么改引用，要么保留。

### 1.3 文档与代码对账

> **工程经验总结 §5.3 的教训**：代码改了，文档没跟上，比代码写错更常见。

必查的**会漂移的数字**：

| 项 | 在哪查 |
|---|---|
| 槽上限 `MAX_SLOTS` | 代码里是几，README/使用说明/架构说明里写的是几 |
| 端口规则 | 代码的 `suggest_port` 与文档描述是否一致 |
| 回归套数 | `ls scripts/test-*.py \| wc -l` 与文档里写的数量 |
| 版本号 | `README` 标题里的版本与 tag 一致 |

```bash
# 一条命令揪出所有过时数字
grep -rn "最多 5\|1~5\|MAX_SLOTS = 5" --include=*.md . | grep -v .workbuddy-ai
```

### 1.4 链接与完整性

```bash
# 文档内部链接无断链
# 所有 Python 文件可解析
# .bat 仍是 GBK + CRLF
python scripts/fix-bat-encoding.py --check
```

## 2. Git 历史清理（只在首次开源时做一次）

> **关键认知：`.gitignore` 只影响"将来不提交"，不影响"已经提交过的"。**

一个文件即使后来被忽略，只要曾经提交过，**它就在历史里，会随仓库推上去**。

### 2.1 判断要不要清理

```bash
# 全历史搜索（含已删除的文件）
git log --all -p 2>/dev/null | grep -nE '<敏感词>' | head

# 只看内容、排除提交作者行
git log --all -p 2>/dev/null | grep -vE '^(Author|Commit):' | grep -nE '<敏感词>'
```

**有命中就要清理。**

### 2.2 清理方式

| 方式 | 适用 | 代价 |
|---|---|---|
| **压缩成单提交**（推荐首次开源） | 开发历史是私人的、没有外部贡献者 | 丢失提交历史 |
| `git filter-repo` | 必须保留历史 | 脚本复杂，所有 commit hash 变化 |

**压缩成单提交的完整步骤**：

```bash
# 0) 先备份（万一后悔）
git branch backup-before-squash

# 1) 修正提交身份
git config user.name  "<GitHub 用户名>"
git config user.email "<用户名>@users.noreply.github.com"

# 2) 建无父提交的分支
git checkout --orphan main
git add -A
git commit -m "Initial release v1.0"

# 3) 删掉旧分支
git branch -D master backup-before-squash

# 4) ⚠ 关键一步：清空 reflog，否则旧提交仍能被找回并推上去
git reflog expire --expire=now --all
git gc --prune=now --aggressive
```

**第 4 步是最容易漏的一步。** 不做的话，`git log` 看着干净，但旧对象仍在 `.git` 里，一旦有人知道 hash 就能取出。

### 2.3 验证

```bash
git log --oneline --all | wc -l          # 应为 1
git log --all -p | grep -cE '<敏感词>'    # 应为 0
```

## 3. GitHub 平台要求

| 要求 | 阈值 | 检查 |
|---|---|---|
| 单文件大小 | 警告 50MB / 拒绝 100MB | `git ls-files -z \| xargs -0 ls -la \| awk '$5>52428800'` |
| 仓库总体积 | 建议 < 1GB | `du -sh .git` |
| 默认分支名 | `main`（2020 年后默认） | `git branch` |
| 必须有 LICENSE | — | `ls LICENSE` |
| README 存在 | — | 首屏说清"这是什么、怎么跑" |

**行尾策略**（`.gitattributes` 必须钉住）：

```
.githooks/*  text eol=lf     # 钩子 CRLF 会让 sh 报 bad interpreter
*.sh         text eol=lf
*.bat        text eol=crlf   # cmd.exe 按 GBK 逐字节解析
```

## 4. 首次使用实测（不可省略）

> **工程经验总结 §5.1**：测试全绿 ≠ 能发布。绿的是"已写进测试的路径"，而"第一次运行"这条路径往往没被覆盖。

**做法：在空目录里从零走一遍。**

```bash
rm -rf /tmp/fresh && mkdir -p /tmp/fresh
git archive main | tar -x -C /tmp/fresh
cd /tmp/fresh
```

然后依次验证：

| # | 场景 | 期望 |
|---|---|---|
| 1 | `python scripts/check-env.py` | 结论「可以运行」 |
| 2 | 双击 `start-manager.bat` | 窗口打开，**自动生成 config.json** |
| 3 | 零槽时界面 | 显示引导卡，不是空白 |
| 4 | `python dsh-tm.py list` | 缺 config 时**自动生成**并提示（不能直接报错退出） |
| 5 | 关闭窗口 | 无残留进程 |

**2026-11-01 实测抓到的真实问题**：第 4 项原本直接报「找不到配置文件」退出——
GUI 会自动生成、CLI 不会，两个入口对首次使用的态度不一致。已修。

## 5. 发版清单（打印出来逐项打勾）

```
□ 1. 隐私扫描四条命令全部 OK
□ 2. 敏感文件已在 .gitignore 中（逐个 git check-ignore 验证）
□ 3. 无引用的一次性文件已删；被引用的一律保留
□ 4. 文档里的数字（槽上限/端口/回归套数）与代码一致
□ 5. 文档内部链接 0 断链
□ 6. 所有 .py 可解析、所有 .bat 是 GBK+CRLF
□ 7. 12 套离线回归全 PASS
□ 8. 空目录实测 5 个场景全过
□ 9. 单文件 < 50MB，仓库 < 1GB
□ 10. LICENSE / README 齐全，默认分支为 main
□（首次开源）11. 历史已压缩 + reflog 已清空 + 验证旧敏感词 0 命中
```

## 6. 后续更新的流程

**每次发新版本，重复 §1 + §5 即可**（§2 只在首次开源做一次）。

### 6.1 版本号约定

采用 [语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`：

| 改动性质 | 版本 | 例 |
|---|---|---|
| 破坏性变更（改 config 结构、改 CLI 参数） | MAJOR | 1.0.0 → 2.0.0 |
| 新增功能（加命令、加界面能力） | MINOR | 1.0.0 → 1.1.0 |
| 修 bug、改文案 | PATCH | 1.0.0 → 1.0.1 |

### 6.2 发版步骤

```bash
# 1. 改代码 + 补测试（新功能必须有断言，否则下次改坏没人知道）
# 2. 更新 README 里的版本号与变更说明
# 3. 跑 §5 清单
# 4. 提交并打 tag
git add -A && git commit -m "feat: xxx"
git tag -a v1.1.0 -m "v1.1.0: xxx"
git push origin main --tags
# 5. 在 GitHub 上按 tag 建 Release，粘变更说明
```

### 6.3 一条硬规矩

> **新增功能必须连带三样东西：测试断言、文档更新、本清单的新检查项（如果它引入新的风险面）。**

只写功能不写测试的提交，会在下一次改动时静默坏掉——这个项目已经吃过亏（见 `docs/工程经验总结.md` §3）。

## 7. 未来：做成 dsh 插件的差异

> 目前是**独立桌面工具**。若将来要发布到 dsh market 作为插件，以下地方要变，**其余检查项通用**。

| 维度 | 独立工具（现在） | dsh 插件 |
|---|---|---|
| 分发 | GitHub Release / 压缩包 | npm 发布 + dsh market 收录 |
| 依赖清单 | 无第三方依赖（纯标准库） | 需 `package.json` 声明 `peerDependencies` 与 `engines.dsh` |
| 入口 | `.bat` → `dsh_manager.pyw` | Cordis 插件 `apply()`，挂到 Slot 上 |
| UI | Tkinter 独立窗口 | 必须用 dsh 的 Web UI 组件（Slot + 主题 token） |
| 配置 | 自己的 `config.json` | 走 dsh 的 Config schema（Schemastery） |
| 兼容性 | 只依赖 Python/Node 版本 | 必须声明支持的 dsh 版本区间，且要跟上 dsh 迭代 |
| 测试 | 离线回归 | 还要有插件加载与卸载的冒烟测试 |

**关键判断**：插件形态要求 UI 用 Web 组件重写、逻辑跑在 dsh 进程内，
**与现在的"独立 Python 进程 + Tkinter"是两套架构**。真要转，是一次重写而不是改包装。

**建议**：先把独立工具做稳、做出口碑；插件化作为独立分支立项，不要混在当前主线里。
