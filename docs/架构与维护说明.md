## 1. 一句话架构

一个 tkinter 小窗口（`dsh_manager.pyw`）读 `config.json`，为每个"版本槽"拼出
`node <bin.js> <extra_args>`，用 `subprocess.Popen` 起进程，并注入该槽自己的 `DSH_HOME`；
运行期用**进程签名**（命令行是否落在该槽的安装目录内）来区分"这个 node 是哪个 dsh"，用来精准停/杀。

**五条隔离轴**（违反任意一条都会互相踩，与 README 第一节同一套表述）：

| 轴 | 隔离手段 | 落到配置里 |
|---|---|---|
| ① 进程 | 每个槽起自己的 node 进程，内存不共享 | `bin_js` + `extra_args` |
| ② 数据 | 每个槽自己的 `DSH_HOME`（会话 / 配置 / 凭据） | `dsh_home`，即槽内 `.dsh-home` |
| ③ 端口 | 每个槽自己的 web 端口 | `port` **和** `extra_args` 里的 `--port`，两处必须一致 |
| ④ 运行时 | 每个槽自带一份 node，装依赖与运行期用同一份 | `node_exe`，即槽内 `node/node.exe` |
| ⑤ 临时目录 | 每个槽自己的 `TEMP`，不互相污染 | `temp_dir`，缺省跟着安装根走 |

> **端口为什么写两遍**：主程序的 `_build_cmd` 真正读的是 `extra_args`，`port` 字段只用于预检与状态显示。
> 两处不一致 = 静默失效，所以 `_check_port_consistency` 会直接拦下来。
>
> **端口补丁（仅老版本需要）**：某些 dsh 版本的 `web --port` 不生效（`parseCmdline` 没把它转给 web-app），
> 这时要在 `$DSH_HOME/profiles/web/cordis.patch.yml` 里把 `webserver` 的 config 整个重述一遍（**替换**语义，
> 要保留的字段必须重述）。模板见 `config/cordis.patch.yml.template`。
> **新版本没有这个限制**，管理器直接用 `--port` 传。
> ⚠️ 该文件**不能只写注释**，空/纯注释会让 dsh 启动失败；要禁用该层得写 `[]`。

## 2. 组件地图

| 文件 | 职责 |
|---|---|
| `dsh_manager.pyw` | GUI + 全部运行期逻辑（本文件是唯一入口，双击即跑） |
| `dsh-tm.py` | 命令行入口（`list` / `status` / `start` / `stop` / `url` / `health`，支持 `--all`）。**不 import GUI 模块**，只共用同一份 `config.json` 与隔离语义；回归 `scripts/test-cli.py` |
| `dsh_kill.py` | 杀进程内核：枚举 node → 命令行签名核对 → 多级回退清理。**不写死任何路径/端口**，签名由管理器注入 |
| `dsh_adopt.py` | 纯算法：版本号纠错、扫已装 dsh、槽位规划（目录名/端口）、`adopt_plan`。**无副作用**，可直接单测 |
| `dsh_install_ops.py` | 纳入 / 一键装官方版：写 `config.json`（原子写 + 备份）、装完复核槽形状、进度回调 |

| `dsh_health.py` | 槽体检：**只读**诊断（程序入口 / node / 数据目录 / 启动脚本 / 依赖齐不齐 / 原生模块 / node 版本 vs `engines` / 跨槽端口冲突）。**不写盘、不改文件**。回归 `scripts/test-health.py` 里有一项专门比对体检前后的磁盘快照。窗口里的「修复…」是另一个函数（`dsh_uninstall_ops.repair_slot`，只补不删，用户点了才跑） |

## 3. 运行期数据结构（改代码前必看）

`dsh_manager.pyw` 顶部按 `config.json` 解析出一套全局变量，**所有流程都只读它们**：

| 名字 | 类型 | 含义 |
|---|---|---|
| `CFG` | dict | `config.json` 原文 |
| `VC[key]` | dict | 该槽**解析后**的运行参数：`label / node_exe / bin_js / dsh_home / port / browser / extra_args` |
| `SLOT_KEYS` | list | 槽顺序（按 `config.json` 的 `versions` 键序）；**上限 `MAX_SLOTS = 6` 个**，超了直接 `_fatal` |
| `SIG[key]` | callable | 该槽的进程签名：`cmdline -> bool`（判据见 §6） |
| `SIG_ANY` | callable | "任何 dsh"的泛签名（命令行含 `@deepseek-ai/dsh`）；**只**用于「杀全部」的槽外兜底 |
| `INSTALLED[key]` | str/None | 该槽 `bin_js` 实际安装的版本（从 `package.json` 读，显示在卡片标题右边） |
| `procs[key]` | Popen/None | 本管理器启动的进程句柄 |
| `auth_urls[key]` | str/None | 该槽的**完整入口 URL（含 token）**，只存在内存里 |
| `_scan_pos[key]` | int/None | 该槽的日志扫描偏移（扫描时留 128 字节重叠） |
| `BUSY` | dict | 长任务（安装/纳入/卸载）期间要冻结的按钮清单：`btns`。2026-10-30 删掉「换版本」后只剩这一项 |

> `browser` 字段不只认 `chrome/edge/firefox/default`，写成 exe 绝对路径也行；`default` 或找不到时退回系统默认浏览器。
> `resolve()` 支持 `<self>`（本文件所在目录）/`<base>`/`<home>`/`<npm_global>` 四种占位符，离线包靠 `<self>` 整目录搬迁。

## 4. 三条流程

### 4.1 启动（`start_one`）

1. 已在跑 → 忽略；
2. `port_open(port)` 预检 → 被占则用 `_pids_on_port()` 查出占用者 PID，弹窗告知（不静默失败）；
3. 有 `dsh_home` 则注入 `DSH_HOME` 并 `_clean_stale_lock()`；
4. **无条件**布防 `auth_urls[key] = None` 与 `_scan_pos[key] = 当前日志大小`（**与是否隔离无关**，见 §5.3）；
5. `Popen(cmd, env=env, stdout=LOG_FH, stderr=STDOUT, creationflags=CREATE_NO_WINDOW)`。

### 4.2 停止 / 杀全部（`kill_one` / `kill_all` → `dsh_kill`）

`find_version_pids(sig, port)` 两轮：① 枚举所有 `node.exe`，命令行命中签名 → 收编；
② 该端口上的监听者，命令行命中签名 → 收编，**不命中 → 记录并拒绝（拒绝误杀守卫）**。
然后每个 PID 先过**执行前签名复核**（`monitor_and_kill(..., sig=)`），再
`taskkill /F` → `taskkill /T /F` → `TerminateProcess`（原生 API），每步回读存活。

> 为什么要复核：候选集是"枚举 → 门控"两步得到的，两次之间进程可能已退出、PID 被系统复用给
> 别的软件。不复核就会把复用该 PID 的**无关进程**杀掉 —— 这是"杀单个版本"最容易伤到别人的路径。
> 复核只在"能查到 node 进程表、且命令行不命中签名"时拒绝；枚举整体失败时才降级放行
> （否则一次枚举失败会让整条清理链路全废）。

**杀全部** = 两槽签名 ∪ 泛签名 `SIG_ANY`：

1. 先按槽各自清理 —— 把"换端口重启后遗留的旧实例""另一个版本"分得清清楚楚；
2. 再用 `SIG_ANY` 兜底清理**槽之外**的 dsh 进程 —— 别的安装位置，以及**不是用 bin.js 拉起的
   子进程**（实测存在 `dsh-subprocess-local/runner.js`、`dsh-sandbox-windows-acl/runner.js`、
   `dsh-host-directory-picker-native/worker.cjs`）。没有这一步，"杀全部"会留下这些残留；
3. 最后再扫一遍端口，仍被非 dsh 进程占用**只告警、不碰**。

### 4.3 安装 / 纳入 / 卸载（都走同一条"长任务"骨架）

三者共用的骨架是 **`_set_busy(False)` 冻结按钮 → 后台线程干活 → 主线程 `root.after` 收尾**：

- `_set_busy()` 冻结 `BUSY["btns"]` 里的全部按钮。为什么必须冻：这些操作会在磁盘上搬
  `node_modules`、改 `config.json`，期间点「启动」会拉起半装状态的实例（2026-10-29 踩过）。
- 耗时操作（`run_official_install` / `adopt_existing` / `uninstall_slots`）都在 `dsh_*_ops.py` 里，
  GUI 只负责传 `progress=prog` 并在 `on_step` 里刷进度窗。
  **`on_step` 必须由 ops 主动调用**——2026-10-29 就出现过进度窗停在「准备中…」，
  实际卸载早已完成，只是漏传了 `progress=`。
- 装官方版的内核是 `dsh_install_ops._npm_install_slot()`：**纯 Python 直调 npm**
  （用本槽 `node/node_modules/npm/bin/npm-cli.js`），不依赖任何 `.ps1`。
  流程 = `npm view` 预检版本 + 选源 → `npm init -y`（缺 `package.json` 时）→ `npm install <spec>`，
  网络类失败（负退出码）自动换镜像重试一次。
- **槽名占用**是 `-2` 后缀的唯一来源（`unique_dir` 发现同名就让位）。两条产生路径都要堵：
  1. **装之前**：目标名若是"零文件空壳"（卸载收尾被占住留下的），`_reuse_empty_shell()`
     清掉并复用原名。判据只有零文件，有一个文件/junction 就不算。
  2. **装失败时**：`_drop_partial_install()` 把本次新建的目录整个收回 + `_unregister_slot()`
     把槽从 config 撤掉，状态退回安装前。为什么必需：失败时目录里已有 `npm init -y` 的
     `package.json`，它**不满足**零文件判据，用户一点「重试」就变成 `dshV1-2`。
     两条安全前提：`bin.js` 不存在（确实没装成）+ `.dsh-home` 零文件（没有用户数据）。
  启动时 `_log_orphan_shells()` 会把现存的空壳点名打进日志，**只报不删**。
- 卸载的备份走 `dsh_uninstall_ops._copy_user_data()`：优先 `robocopy /E /XJ /MT:8`
  （不跟随 junction，实测比逐文件快约 3 倍），失败退回逐文件并逐个记录拷不动的文件。
- `on_done` 只由线程包装器调一次；ops 自己再调会弹两个框。
- 收尾统一刷新 `INSTALLED` 与卡片标题，然后 `_set_busy(True)` 解冻。

> 2026-10-30：原 §4.3 的「换版本」流程（`open_swap_dialog` → `_start_swap` → `_swap_worker` →
> `_poll_swap` + `SWAP` 状态机 + `scripts/switch-version.ps1`）已整体删除。
> 现在换版本 = 卸载 + 装官方版。
> **注意**：那个脚本当年不只服务换版本，安装流程也在调它；删除时漏改安装，导致
> 「安装官方版」报 `[WinError 2]`。所以安装内核才改成纯 Python —— 少一个共享脚本，
> 少一处"删了别处崩"的可能。

## 5. 日志与 token 脱敏（本项目最"反直觉"的一块）

### 5.1 为什么必须脱敏

`dsh web:` 启动时会打印 `http://127.0.0.1:<port>/?token=<随机>`，那个 token 是该实例的**唯一认证凭据**
（新版 dsh 无 token 请求 `GET /` 直接 401）。而 README/FAQ 又鼓励用户把 `dsh-manager.log` 发出来排查。
所以：**token 不能留在日志里**。

### 5.2 为什么不能把子进程输出改成管道（可读可不读，但别改）

dsh 源码里**没有任何 `EPIPE` / `process.stdout` 错误处理**（在 `0.1.5-rc.2` 的 `@deepseek-ai` 包树里 grep `EPIPE` 零命中）。
如果为了脱敏把 dsh 的 stdout 接到管道：**管理器一退出、管道读端关闭，正在运行的 dsh 下一次写 stdout 就会因 EPIPE 崩掉** ——
用户关掉管理器、浏览器里的 dsh 随即挂掉，这是最糟的失败模式。因此本项目的做法是：

- 子进程 → **日志文件句柄（append）**，崩溃安全；
- 需要脱敏 → 对同一文件做**等长就地覆盖**（`_mask_span`）：把 token 的字符原地换成 `*`，**文件长度不变**。
  长度不变是关键：既不影响子进程继续 append（它按 O_APPEND 写到 EOF），也不影响管理器自己的扫描偏移。

### 5.3 三层脱敏

| 层 | 覆盖范围 | 实现 |
|---|---|---|
| ① `log()` 出口 | 管理器自己写的所有文本 | 正则 `_TOKEN_TEXT_RE` 统一打码 |
| ② `_scan_slot(key)` | dsh 子进程写的**本槽端口**入口行 | 抓完整 URL 进内存 → 把该行 token 就地等长打码；**只处理本槽端口**，避免两槽互相把对方的 URL 打码后抓不到 token |
| ③ `_scrub_existing_log()` | 启动时的**历史**日志全量 | 等长覆盖所有 `token=xxx`（含旧版本管理器写的 `打开浏览器 -> ...?token=` 行） |

**替代能力**：完整 URL 一直在 `auth_urls`（内存）里，界面上的「**复制入口 URL**」按钮把它写进剪贴板 —— 既能粘到任意浏览器 / 别的机器，token 也不落磁盘。
> 这正是"为什么要有这个按钮"：脱敏砍掉了文档里记载的"从日志复制 URL"，这个按钮把它还回来了。**没有它，脱敏就是功能倒退。**

### 5.4 ⚠️ 一个反直觉的事实：token 需求是**版本**属性，不是"隔离"属性

| 版本 | 入口 URL | 源码依据 |
|---|---|---|
| `0.1.0-rc.8` | **无 token** 的裸 `http://127.0.0.1:<port>` | 它的 `dsh-web-app` 里 `localWebUrl()` 直接返回裸 loopback 地址；其 `dsh-client-connection` 自述 "explicitly not authentication" |
| `0.1.5` 起 | 带 token | `dsh-client-connection` 有 `TOKEN_QUERY = "token"` / `launchToken`，`dsh-web-app` 打印的变量名就叫 `authenticatedUrl` |

历史教训：旧代码曾用 `token_required = bool(dsh_home)` 来猜 —— 那是把"是否隔离"当成"是否需要 token"。
后果是**把 v1 槽换到 0.1.5+ 之后**，`token_required` 仍为 False（因为 v1 的 `dsh_home` 是 `null`），
于是「打开」会开一个无 token 的地址 → 401；更隐蔽的是它的 URL 扫描**从不布防**，事后想补救都抓不到。
**现在不再猜：每个槽都布防，抓到就用。**

### 5.5 token URL 到底是什么（白话）

**先给结论：它是"进门钥匙"——每次启动换一把、不存在任何文件里、不跟文件夹走，所以和你把管理器拷到哪台电脑毫无关系。**

1. dsh 的网页版是跑在你自己电脑上的一个本地网站（`127.0.0.1:<端口>`）。只有本机能连它 —— 但"只有本机"不等于"安全"：你电脑上任何程序、任何浏览器扩展、甚至你随手打开的某个网页里的脚本，都能往 `127.0.0.1:4080` 发请求。
2. 所以新版 dsh 启动时**随机生成一串口令（token）**，拼进入口网址：`http://127.0.0.1:4080/?token=<每次启动都不一样>`。
3. 服务器只认两种请求：**带正确 token 的**，或者**之前用带 token 的网址访问过、已经被种下 cookie 的浏览器**。
4. 类比：token 相当于**门禁卡**，第一次必须刷卡进门；进门后门禁给你发一张 **30 天有效**的通行证（cookie）。此后在同一个浏览器里直接敲 `127.0.0.1:4080` 就不用再刷卡了。

它有三个关键性质，理解这三个就够用了：

| 性质 | 含义 |
|---|---|
| **每次启动重新生成** | dsh 一重启，旧的那串立即作废；所以**不能把带 token 的 URL 存下来下次用** |
| **只活在内存与 URL 里** | 不写进 `settings.yaml`、`config.json` 或任何配置文件；关掉进程就没了 |
| **只对本机有效** | 它是"本机这个网页的进门钥匙"，跟你的账号、API Key 无关 |

由此直接推出两件事：

- **把管理器文件夹拷到新电脑，不用管 token** —— 新电脑上第一次启动会生成全新的一串（每台机器各自独立生成）；
- **只有"复制入口 URL"按钮和"打开浏览器"按钮能拿到完整的 URL** —— 日志里那份已被打码（§5.1–5.3），这正是那个按钮存在的理由。

**为什么 0.1.0-rc.8 完全没有这回事**（§5.4）：旧版只靠"不能跨站请求"这类浏览器侧限制，新版才加了进程级 token。这也是"要不要 token 看版本、不看是否隔离"的由来。

## 6. 进程签名模型

**槽签名** = 命令行是否落在该槽的**安装目录**内（取 `bin_js` 里 `/node_modules/` 之前那一段），
比较前两侧都先**归一化**（反斜杠→正斜杠、转小写、合并重复分隔符）。

- 安装根每槽唯一 → 天然区分 v1 / v2 / 别的 app 的 node；
- 判据用"安装根"而不是"bin.js 字面量"，是为了覆盖**同一份安装里不是 bin.js 拉起的子进程**
  （实测出现过 `dsh-subprocess-local/runner.js`、`dsh-sandbox-windows-acl/runner.js`、
  `dsh-host-directory-picker-native/worker.cjs`）—— 按 bin.js 匹配会漏杀它们；
- **必须归一化**：Windows 上 `C:\a/b\c` 与 `C:/a/b/c` 是同一路径但字符串不等。实测同一份 v2，
  用 `config.json` 的路径拉起时命令行是**混合斜杠**，用 bash 拉起时是**全反斜杠** —— 不归一化，
  签名就会随"谁拉起来的"而失配，表现为**杀不掉自己的进程**（实测：旧签名对全反斜杠启动的 v2
  判 `False`，新签名判 `True`）；
- `SIG_ANY` = 命令行含 `@deepseek-ai/dsh`（dsh 及其子包的路径必然含此串）。**只**用于「杀全部」的
  槽外兜底。实测：全部 node 进程里只有 dsh 的命中，其它应用（各类 MCP 服务）的
  node 进程不命中；
- 签名由 `config.json` **动态构造**（`_make_sig`），换机器、换槽位自动跟着变；
- **不要**再引入 `--port` / `--profile` 这类附加条件。历史上就是因为要求字面量 `--port 3080`，
  导致「裸敲 `dsh web`、`dshvm` 连接器、手写启动器」启动的**同版本**进程清不掉，
  而界面还提示"点『杀全部』清理" —— 提示与行为自相矛盾（「杀全部」用的是同一套签名）。
- 已知代价：如果某种启动方式**完全不经过该安装目录**（例如另装一份同版本副本），槽签名对不上，
  会被当作"外部占用"而**拒绝清理** —— 槽内这条路径是**故意的**（宁可拒绝，不可误杀）。
  这类进程归 `SIG_ANY` 管，点「杀全部」时会被兜底清掉。

## 7. 红线（踩过坑才写进来的）

1. **子进程输出不要用管道**（§5.2，EPIPE 会杀掉正在跑的 dsh）。
2. **不要用 `str(pid) in 输出` 判进程存活**：`pid=123` 会命中 `1234` 或内存列的 `1,234`。
   现在用 `tasklist /FO CSV /NH` 精确取列；查不到（非 0 返回）一律判"不存在"，
   安全性由 `_holder_is_this_slot()` 兜底（核对失败时保守保留锁，不会误删）。
3. **不要用端口子串匹配**：`":3080" in line` 会命中 `:30800`、`:30801`。按列解析 `local address`。
4. **`config.json` 只能原子写**（临时文件 + `os.replace`）。直接 `open(w)` 会先截断；中途崩溃 = 管理器再也打不开。
   启动时已加自愈：解析失败 → 备份为 `config.json.bad-<时间戳>` → 从 example 重建。
5. **安装/纳入/卸载期间要冻结所有按钮**（`_set_busy`），否则可能在 npm 正搬 `node_modules` 的半装状态下被"启动"。
6. **最多 6 个槽**（`MAX_SLOTS = 6`）：界面按"每槽两列"自动排布（1~6 槽 → 2~12 列，由 `COLS = len(versions)*2` 驱动）。加槽只需在 `config.json` 加一个版本键，布局代码已通用；要超过 6 个只需调大 `dsh_manager.pyw` 与 `dsh-tm.py` 的 `MAX_SLOTS`（两处必须一致，`test-cli.py` 的 B4 断言锁着）。

7. **界面显示偏好**（2026-10-31）：`config.json` 顶层可选的 `ui` 段决定**画哪几张卡片**：

   ```json
   "ui": { "max_visible": 4, "order": ["v2","v1","v3","v4"], "visible": ["v2","v1","v3"] }
   ```

   - `order` 是左右顺序；**没记过的槽自动接在末尾** —— 新装的槽是 append 进 `versions` 的，
     不兜底就会出现「装了新版本，界面上看不见它」。
   - `visible` 缺省 = 全显示；`max_visible` 是硬上限（1..`MAX_SLOTS`）。
   - 三者都只影响渲染：`SLOT_KEYS` / `VC` / 进程 / 端口 / 卸载名单永远是**全量**（隐藏 != 卸载）。
   - 卡片由 `_build_cards()` 画，可反复调用原地重画：先 `_clear_cards()` 销毁旧控件、
     **复位列配置**（不复位的话旧列仍吃宽度，卡片被挤到左边）、把旧按钮从 `BUSY["card"]`
     里摘掉（否则 `_set_busy` 会去 configure 已销毁的控件）。
   - 因此改设置**即时生效**；装/卸改的是 `SLOT_KEYS` 本身，那种仍要重启。
   - 纯逻辑在 `dsh_ui_prefs.py`（`.pyw` 不可 import，留在里面测不了），回归
     `scripts/test-ui-prefs.py`。

8. **拖拽排序（手机式）**（2026-10-31）：按住卡片**任意位置**（含按钮）往外拖 ——
   卡片从格子里"抽"出来浮在其它卡片上方跟着鼠标走，其它卡片实时让位，松手落下并写回
   `ui.order`。四条实现约束，违反任何一条都会「拖一下就卡死 / 拖完顺序丢了」：

   - **拖动期间绝不能调 `_build_cards()`**。它会 `destroy` 全部卡片，正在拖的那个控件
     一起没了 → 松手事件送不到 → 拖动卡死。拖动中只走 `_layout_slots(order, gap)`：
     改 `grid` 列号 + 重建分隔线，**卡片控件活着**。
   - **浮起来的卡片靠 `place()`**，而且必须显式给 `width=` / `height=`：`grid_forget()`
     之后 `place` 默认用控件请求尺寸，卡片会缩水。浮起前要记下鼠标在卡片内的偏移，
     否则卡片会"跳"到指针底下。落回时要先 `place_forget()` 再 `grid()`（两个管理器不能并存）。
   - **"让位"靠空洞**：`_layout_slots(others, gap=N)` 把其余卡片按落点重新排到
     0..n-1 个槽里、**跳过第 N 个槽**，那一列不放控件但保留列宽 —— 就是空出来的位置。
   - **按钮也要能拖，但松手要吞点击**：`_bind_drag(..., is_btn=True)` 给按钮挂
     `_drag_end_btn`，真拖过就 `return "break"`。ttk 的按钮命令在**类绑定**里执行，
     widget 级绑定先跑，`break` 之后命令不会执行 —— 否则"拖完卡片顺手启动了一个版本"。

   其它细节：8 px 位移阈值（x/y 都判，单纯点一下不会把卡片拿起来）；拖回原位不写盘；
   写盘失败用 `root.after(0, _build_cards)` 推迟重建（不能在按钮的 `<ButtonRelease>`
   处理里销毁控件）；`_clear_cards()` 必须清 `CARD_WIDGETS` / `CARD_SEPS`；
   浮起时换 `Lifted.TLabelframe` 样式（clam 主题认 `bordercolor`）并在右下贴一块
   灰色 `tk.Frame` 当影子，松手销毁。落点只看**其它**卡片的中线（`_drag_target`），
   最左/最右自然得出 0 / len(others)；只重排显示中的槽（`UIP.merge_display_order`）。
   motion / release 额外挂在 toplevel 上兜底（bindtags 每个子控件都带这一层），
   不依赖 tk 的隐式 grab。设置对话框的列表也支持拖行（`return "break"` 阻止 Listbox
   自己的拖选改掉选中区）。

9. **`CREATE_NO_WINDOW` 会让 `node-pty` 的 conpty agent 报 `AttachConsole failed`**（日志里能看到，非致命，`pwsh` 工具仍可用）。要治它得给子进程一个可 attach 的 console，代价是可能闪控制台窗口——目前选择保留现状。
10. **别用 PowerShell 的 `Set-Content -Encoding utf8` 改 `config.json`**：Windows PowerShell 5.1 会写出 UTF-8 **BOM**（`0xEF 0xBB 0xBF`），而 Python 的纯 `utf-8` 读取会直接抛 `Unexpected UTF-8 BOM`，把一份**好配置**判成坏配置。
   - 读一律用 `encoding="utf-8-sig"`（自动吃掉 BOM）；
   - 写用 Python 的 `open(..., "w", encoding="utf-8")`（不带 BOM）；
   - **自愈路径必须弹框**（pythonw 没有控制台，`print` 等于没说），否则就是"静默把你的真实配置换成示例模板"。

   > 这条不是纸上谈兵：开发过程中真的踩过一次 —— PowerShell 写 BOM → `json.load` 抛错 → 自愈把真配置改名并用示例重建，全程静默。

## 9. 改完怎么验证（照这个清单走，别跳）

### 一条命令自检（推荐）

```bat
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check-all.ps1
```

它检查 6 件事（零依赖、不联网，全量约 3 秒 + 回归测试约 30 秒；`-Fast` 跳过回归）：

> **先解 Python 解释器**（`0/6` 一节）：`py` 是 python.org 安装器的 "py launcher" 组件，
> Microsoft Store / WindowsApps 版 Python **不带它**。本机就属于后者，所以脚本自动按
> `python` → `py` → `python3` → 常见安装位置 依次探测；也可显式指定 `-Python <路径>`。
> （早期硬编码 `py`，导致 Store 版 Python 的自检固定失败 2 项、pre-commit 拦住任何提交。）

| # | 检查 | 为什么有这一条 |
|---|---|---|
| 1 | Python 语法（`scripts/py-syntax-check.py`，**内存编译、不写 `__pycache__`**） | 语法错要在写入前拦住 |
| 2 | 编码策略：`.ps1` **必须**有 BOM；`.json`/`.md`/`.py` **必须没有**；`.bat` 必须是 **GBK + CRLF + 无 BOM**，仓库内走 `fix-bat-encoding.py --check`、**生成到槽目录的那三份**走 `fix-bat-encoding.py --slots --check`（`check-all.ps1` 两项都跑）；**子进程 `text=True` 必须带 `encoding`/`errors`** | 这是本项目踩过最贵的坑：① BOM 曾导致配置被静默替换；② 子进程编码坑见 §7；③ UTF-8（无论有无 BOM）写的 `.bat` 会让 cmd.exe 按 GBK 字节边界**撕裂相邻中文 REM 行**，后半截被当命令执行 → `<`/`>` 触发重定向 →「命令语法不正确」rc=255，双击窗口一闪就没（实证：`dsh-cli.bat` 双击无反应，2026-10-15 修复）。注意 `check-all.ps1` 仓库内那条检查**扫不到**槽目录里生成出来的 bat，必须靠 `--slots` |
| 3 | `git ls-files` 里的 `config.json` / `*.log` / 凭据 | 防止配置与运行产物入库 |
| 4 | 文档与日志里是否出现完整 `token=...` | 脱敏机制失效时能立刻发现 |
| 5 | Markdown 相对链接能否落地（逐个 `Test-Path`） | 文档搬动/改名后最容易断 |
| 6 | 离线回归套件（`-Fast` 时跳过） | 行为回归 |

**已挂 pre-commit 钩子**（走 `-Fast`，秒级）：

```bat
git config core.hooksPath .githooks      :: 每台机器一次
git commit --no-verify                   :: 确实需要跳过时
```

> 自检脚本本身也会犯错（例：用 grep 找"恒真断言"时会命中注释里引用的那个反模式）。所以**检查器的输出仍要人判断**，不要盲信。

### 手动命令（钩子之外的补充）

```powershell
# 1) 语法（管理器目录指仓库根）
python -m py_compile <管理器目录>\dsh_manager.pyw <管理器目录>\dsh_kill.py

# 2) 全量自检（语法 + 编码 + 敏感文件 + token + 文档链接 + 全部离线回归）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\check-all.ps1

# 3) 真机启动（人工看一眼）
python <管理器目录>\dsh_manager.pyw
#   → 窗口能出现、两槽标题显示「≡ dshVx · <正确版本>」、状态行自动刷新
#   → 点「启动」等到 ✓，点「打开 <浏览器>」能进界面（而不是 401）
#   → 翻 dsh-manager.log：不该出现完整的 token=<一长串随机字符>
```

测试脚本的设计要点（想扩测就照它写）：**不复制一份逻辑来测**，而是从 `dsh_manager.pyw` 里按函数抽源码 `exec`，
所以测的就是即将运行的那段代码；`tasklist`/`netstat` 这类环境相关的分支用"注入伪造输出"确定性验证。

> ⚠ **这个设计有已知盲区**：注入伪造输出能确定性地测「**解析**逻辑」，但会**绕过真正的 `subprocess` 调用与解码**。
> `_pid_ports()` 恒返回空那个 bug 正是这样活下来的：
> 解析逻辑被测得好好的，坏的是"拿到 `None` 而不是文本"这一段。所以
> **凡是"外部命令输出 → 解析"的链路，除了注入测试，还要有一条真调外部命令的烟测**（例：断言 `len(_pid_ports()) > 0`）。

### 测试设计三条规矩（都是踩过坑才写的）

1. **不依赖可变的真实状态**。反例：早期测试从真实的 `dsh-manager.log` 里找明文 token —— 脱敏修好后，
   这个前提必然失效，于是"修复生效"反而让测试假失败。现在改为**自造 fixture**（固定 token、固定行）。
2. **禁止恒真断言**。反例：`if _pid_alive(x): check(..., True)` —— 在已经为真的分支里再断言它真，等于没测。
   正确写法是先探一次环境能力，探不到就 **SKIP（不计失败）**，探到了就断言**真实表达式**。
3. **环境不具备 ≠ 测试失败**。沙箱里 `tasklist` 被拒、外网被拦，这些是能力缺失，应 SKIP 并显式打印，
   而不是让套件飘红 —— 否则真失败会被淹没在噪声里。

### 改文件的方式（协作约定，2026-09-14 起）

- **优先用原生编辑工具做原地修改**（字面匹配 + 唯一性检查 + 自带 diff），而不是"生成一个 Python 补丁脚本来改文件"。
  后者等于把目标文本再塞进一层字符串字面量，会额外引入引号转义、反斜杠 `\n`、编码等一整类低级错误，
  而且一个补丁脚本动辄几 KB～几十 KB。
- **事务边界交给 git**：批量修改中途失败，`git checkout -- .` 即可回到干净状态，不需要脚本自己实现"全中或全不中"。
- **什么时候才写补丁脚本**：确实需要一份**能在另一台机器重放**的产物时。那种情况应把 old/new 文本存成**独立文件**让脚本读，
  而不是写成 Python 字符串字面量。

## 10. 已知限制 / 后续可做项

- **最多 6 个版本槽**（`MAX_SLOTS = 6`；界面布局：每槽 2 列，N 槽 → 2N 列，由 `COLS` 驱动）。要扩到更多槽只需调大 `dsh_manager.pyw` 与 `dsh-tm.py` 里的 `MAX_SLOTS`（两处必须一致），布局代码已通用。
- **`config.json` 的 `label` 会与实际版本漂移**（本机现状就是 `0.1.5 rc.1` vs 实装 `0.1.5-rc.2`）。
  现有机制：`label` 只作为显示名（默认固定为 `dshVx`），可以手动改。**真值永远看标题右边那串版本号**。
- **`AttachConsole failed`**（§7.7）只在日志里出现，未根治。
- `dsh_kill.py` 里有一份与 `dsh_manager.pyw` 重复的 `_pid_alive` 实现（那边仍用子串匹配）。
  影响面：它只用于杀进程后的"还活着吗"确认，判"活"是安全方向，所以暂未合并。
- `docs/DeepSeek-Harness使用手册.md` / `简明手册.md` 是**官方向通用手册**，与本管理器的实现无关，不需要跟着改。

### 10.1 备份 / 卸载 / 纳入 / 移出的安全边界与残余风险（2026-10-31 复查）

**四条硬承诺**（都有离线回归守着）

| 承诺 | 实现 | 回归 |
|---|---|---|
| 不删用户数据以外的任何东西 | `plan_slot` 只列槽根**顶层**子项，逐项过 `is_safe_to_delete`；`purge_root` 只用 `os.rmdir`（只删空目录）；`_force_rmtree` 碰到 reparse point 只摘链接、绝不进去删目标 | `test-slot-ops.py` C/F 组 |
| 备份**要么完整、要么中止** | 拷完 `verify_backup` 逐文件核对（相对路径 + 字节数）；`missing` 或「拷不动」任一非空 → 改名 `-INCOMPLETE`（改名失败则写 `_INCOMPLETE.txt`）+ `raise`，槽目录一个文件都不删 | `test-slot-ops.py` H 组 |
| 删了管理器，各版本照常跑 | 槽自带 node / 本体 / 数据目录 / 三件 bat，bat 内全是绝对路径；预检 fail-open；`kill` 脚本缺依赖时优雅退出 | `test-standalone.py`（真跑 cmd + node） |
| **移出管理不碰磁盘** | `detach_slots` / `readd_slots` 只改 `config.json`（`versions` ⇄ 顶层 `detached`），全程无 `rmtree` / `remove` / `copytree`；移出后槽仍能自己跑（同上一条） | `test-slot-ops.py` I 组（逐文件比对 md5） |

**残余风险**（都**没有**自动处理，需要用户/维护者知情）

| 风险 | 触发条件 | 后果 | 现状与缓解 |
|---|---|---|---|
| **备份里是明文凭据** | 总是 | `.dsh-home` 含登录 token / API key，备份目录 = 一份明文凭据副本 | 备份只落在本机 `dsh备份\`，不上传、不加密。仓库的 `.gitignore` 已排除 `dsh备份/`、`dsh-versions/`、`.dsh/`、`.credentials.yaml`；**别把备份传到网盘/公开仓库** |
| 备份与源**同盘** | 总是 | 盘坏 → 数据与备份一起没 | 这是"误删/误操作"的保险，不是"硬盘故障"的保险。重要数据请自行另存一份 |
| 备份期间源被改写 | 该槽 dsh 没停干净 | `size_changed` 只记 warning，**不阻断** | 文件都在，内容是"那一刻的快照"。提示里会明说；想拿到一致快照请先停槽 |
| `_links.json` 里的链接**没复制** | `.dsh-home` 里有 junction（dsh 插件挂载就是这么做的） | 备份目录里那些插件目录是空的，恢复要手工重建链接 | 清单记了相对路径 → 目标；`dsh_adopt.relink_home` 是现成实现，但**没有 GUI 入口** |
| 槽根不在 `versions_root` 之下 → **拒绝卸载** | 手工把槽配到别的盘/别的父目录 | 该槽永远卸不掉（只在配置里保留） | 刻意的：宁可拒绝，也不按猜出来的边界删。安装根锁死后正常流程不会出现 |
| 纳入时 `shutil.copytree(node_modules)` 会**跟随** node_modules 里的 junction | 用 pnpm / 手工 link 装过插件 | 可能把槽外内容整份复制进来（变大、且变成副本不是链接） | 已知未修：dsh 本体用 npm 装，正常不会出现。若遇到，改用「安装官方版」重建该槽 |
| 只读附件对象文件 | `.dsh-home/attachments/**/objects/` 是 `-r--r--r--` | 备份里也是只读 → 想删备份要先清只读位 | `_force_rmtree` 删槽时会先 `chmod +S_IWRITE`；**删备份目录**目前没这层，用 `rmdir /s` 或先 `attrib -r` |
| 强杀 dsh 会在 TEMP 留垃圾 | 强杀 | `dsh-acl-skill-*` / `dsh-spill-*` 残留，条数≈强杀次数 | 不自动清（怕误删正在用的）；槽体检 > 20 项时提示，**只报不修** |
| 卸载后 `temp_root/<槽>` 仍在 | 总是（临时目录在槽根之外，不归槽所有） | 一个空的临时目录残留 | 卸载收尾的提示里会列出来，可手删 |
| 移出管理的槽**不在**扫描范围 | 移出后又换了安装根 | 「扫描已装 dsh」发现不了它（只扫当前 `versions_root` + npm 全局） | 靠 `config.json` 顶层 `detached` 记录（存**绝对路径**）兜底：扫描时会把这类记录并进候选并原样接回。**手工删掉那条记录 = 失去这条路** |
| 移出后端口无人协调 | 移出的槽和新槽撞同一个端口 | 两个 dsh 同时启动会有一个起不来 | 重新纳入时若端口已被别的槽占用会明确警告；移出状态下管理器不管，只能自己看端口 |
| 单实例互斥只防「同机再开一个管理器」 | 总是 | 两个管理器同时改 `config.json` 会互相覆盖 | 互斥体保证只有一个实例；`write_config_atomic` 读-改-写 + 原子替换兜底 |

**自查清单**（出问题时按这个顺序看）

1. 备份是否完整：打开备份目录里的 `_meta.json`，看 `verify.checked / missing / copy_failed`；
   目录名带 `-INCOMPLETE` 或里面有 `_INCOMPLETE.txt` = 这份不能当后悔药。
2. 卸载为什么中止：管理器日志里搜 `中止：备份失败` / `删不掉`。
3. 卸载后槽目录还在：`next` 次装同名槽会变成 `-2`；确认备份无误后手删。
4. 各版本还能不能自己跑：直接双击槽里的 `dsh.bat`（不经过管理器）。
5. 移出的槽找不到入口：看 `config.json` 顶层 `detached`（每条含 `label` / `root` / `port` / `version`）；
   有记录就能在「卸载 / 移出管理」窗口里重新纳入，没记录就只能靠「扫描已装 dsh 并纳入」或手工。

## 附：与外部工具的关系

本管理器**自己拼命令行 + 注入 `DSH_HOME`**，因此与 `@dsh-so/dshvm` 这类全局版本管理器**互不干扰**：

- `dshvm` 的激活是**全机器一个指针**（`~/.dsh-versions/current-bin.txt`），裸敲 `dsh` 只代表一个版本；
- 管理器按槽各自钉死，两槽可同时跑；
- 本机还另有一套终端入口 `%APPDATA%\npm\dsh-rc8.cmd` / `dsh-dev.cmd`（各自钉 `DSH_HOME`），
  与管理器并存不冲突 —— 而且因为签名只认 bin.js，**管理器里点「杀全部」能把它们起的进程一并清干净**。
